# ADR-0126: grauwolf studio – the AgentWeaver frontend on a Rust backend

- **Status:** Accepted (User, 2026-11-16/17: "a fork of AgentWeaver, which is my project: remove the complete Kotlin backend and build the frontend against a new Rust backend, with the new functions and interfaces"; name "Grauwolf Studio"; decisions Q1–Q11 below)
- **Date:** 2026-11-17
- **Supersedes:** [ADR-0092](0092-agentweaver-export-backend.md), which made grauwolf one more export backend inside AgentWeaver.
- **Related:** ADR-0018 (node catalog), ADR-0109/0110/0111 (identity, delegation), ADR-0120/0121 (grauwolf-k8-ops), ADR-0124 (tool catalog).

## Context
AgentWeaver is the owner's visual editor for agent graphs:
- **Frontend:** Next.js, a Rete.js canvas, Monaco, shadcn and zustand.
- **Backend:** Spring Boot / Kotlin, with about 47 endpoints in 15 areas: workspace as a Git repo, VFS, build, export and review, preview with agent chat, runtime deployment, keys, skills, discovery, GitHub login, and the editor as an MCP server with live sync.
- **Export:** Kotlin/Koog projects.

grauwolf now covers the agent runtime, code generation, deployment, identity and a tool catalog in Rust. Keeping a Kotlin backend that translates into grauwolf would mean two models and two stacks.

## Decision
1. **Name and place (Q1).**
   - The application is **grauwolf studio** (written lowercase like the project).
   - It is developed **locally in this repository** for now: the frontend under `studio/web/`, the backend as the app crate `crates/apps/grauwolf-studio`.
   - There is no GitHub fork; nothing is pushed until the owner says so.
2. **What the canvas edits (Q2, Q8 b).**
   - The canvas loads and saves **grauwolf spec JSON directly**; one harness is one spec.
   - The layout lives beside it in `<spec>.layout.json`.
   - Node kinds come from grauwolf's node catalog (ADR-0018), so each canvas node is exactly one spec construct.
   - A spec is interpreted (`spec serve`) or generated into a Rust crate and image.
   - The Kotlin/Koog export targets (Spring Boot, Ktor/Wasm, KMP) are dropped. A later export may keep the LLM review of the generated Rust code.
3. **API (Q3).**
   - A new, versioned `/api/v1` around grauwolf, not a copy of AgentWeaver's REST shape.
   - The backend publishes an OpenAPI description; a TypeScript client for the frontend is generated from it.
   - The frontend's clients are moved area by area.
4. **Sign-in (Q4).**
   - GitHub, as today. GitHub also gives the workspaces (Git repos).
   - Entra ID sign-in, and runs on behalf of people through ADR-0111, come later.
5. **New functions after the MVP (Q5), in this order:**
   1. tool catalog (browse, policy and signature, drag a package in as tool node);
   2. deployment through `grauwolf-k8-ops` (replacing the kaniko/rollout runtime tab);
   3. identity: a cron node becomes `schedule add` with a grant, plus `identity allow`;
   4. live view of events and traces, with approvals in the editor;
   5. spec tools: validation at the node, the `spec egress` view.
6. **The MVP (Q6, Q9 a):**
   - GitHub sign-in and `GET /me`;
   - workspaces as GitHub repos: list, open, save on a branch of its own, open a pull request;
   - specs: read, write, `validate` with JSON pointers mapped to nodes, `diagram`, `schema`, and the node kinds for the palette;
   - a preview run with chat and live events over SSE;
   - discovery of Ollama, models and MCP servers;
   - API keys;
   - the editor as an MCP server with live sync, so Claude Code can draw along.

   Build, export/review and runtime are left out of the MVP and come back through decision 5.
7. **Taking over the frontend (Q7 a).**
   - `agentweaver/frontend` is copied once to `studio/web/`, without `node_modules` and without AgentWeaver's Git history.
   - From then on it evolves on its own. Kotlin-only parts (export targets, Gradle, Koog terms, the JVM/Native/Wasm build view) are removed step by step.
8. **Preview runs (Q10 a).**
   - They run **in the studio process**, with the grauwolf interpreter as a library.
   - Each run has a budget, and only the tools of the spec are available.
   - A pod per run (`spec serve`) can come later.
9. **Operation (Q11 a).**
   - One binary, `grauwolf-studio`, serves the API and the statically exported Next.js frontend.
   - One image; later deployable with `grauwolf-k8-ops`.
10. **Files of the workspace (Q12 a, User 2026-11-17).**
    - The workspace folder **is** the file system of the studio; there is no separate virtual file system as in AgentWeaver.
    - A file API (`/api/v1/files`: tree, read, write, create, rename, delete, with the same path rules as the specs) serves everything a spec refers to: tool code (`code_file`, `tool_files`, `tools_dir`), `code` nodes, skills, knowledge documents.
    - The frontend shows a file tree instead of the bare spec list and edits files in Monaco (`.rs`, `.md`, `.json`, text).
    - A referenced file opens from the inspector; a missing one can be created from a template.
    - In part 2 the same folder is the Git checkout of a GitHub workspace.
11. **Workspaces as separate projects (W1–W7, User 2026-11-17)** – before part 2, as part 1e.
    - **W1, where they live.** A root folder (default `~/grauwolf-studio/workspaces/`) with one folder per workspace, its metadata in `.grauwolf-studio/workspace.json` (name, description, created, `source`). Existing folders elsewhere can be **registered** too (e.g. `docs/user-guide/examples` or an existing project); the list is a registry file in the root folder.
    - **W2, API.**
      - `GET`/`POST /api/v1/workspaces`; `GET`/`PATCH`/`DELETE /api/v1/workspaces/{id}`.
      - The specs and files routes move under `/api/v1/workspaces/{id}/…`.
      - Deleting a registered folder removes only the entry; deleting an own workspace deletes its folder after a confirmation.
      - `serve --workspace <dir>` keeps working as a single workspace.
    - **W3, UI.**
      - A workspace switcher at the top left with the recently opened ones.
      - A start page without an open workspace: the list, "New", "Register folder".
      - The workspace in the URL (`?w=<id>`).
    - **W4, templates for a new workspace:** empty (with a first spec), the user guide's examples (a copy), a copy of another workspace. "From a GitHub repo" comes with part 2b.
    - **W5, what a workspace separates:**
      - specs and files;
      - the tool policy (`grauwolf.toml`) and the lockfile;
      - knowledge and memory paths;
      - later preview runs and the GitHub link.

      API keys stay per user, for all workspaces.
    - **W6, prepared for GitHub.** `source` is `local` now, later `github` with repository and branch.
    - **W7, transition.** `scripts/studio.sh` starts on the root folder and registers the existing `~/grauwolf-studio-workspace` once as the workspace "examples"; its files stay where they are.
12. **Named ports in the overview (P1–P5, User 2026-11-17)** – part 1f.
    - **P1, the agent node's ports** (grouped, User 2026-11-17: "too many ports – only groups"):
      - Inputs:
        - **Input** (the spec's `input` type);
        - **Tools**: tools, tool files, `tools_dir`, built-in groups, tool packages, self-built tools;
        - **Agents**: `agent_tools`, local and remote;
        - **Resources**: MCP servers, knowledge, long-term memory;
        - **Skills**.
      - One output: **Output** (the spec's `output` type).
      - Each resource node has one output "Agent" and fits only its group's port. Within a group, resource kinds keep their own colours.
    - **P2, connecting.**
      - Connecting a resource to its port writes it into the spec.
      - Disconnecting takes it out of the spec but keeps the node on the canvas as "not connected" (dashed, grey), its configuration parked in the layout file.
      - Deleting the node removes it completely.
    - **P3, the palette** places new resources unconnected next to the agent; the connection writes them into the spec.
    - **P4, agents of the workspace.** Another spec of the workspace can be dragged onto the canvas as an agent node; connected to "Agents" it becomes an `agent_tools` entry referring to that spec. The overview shows who calls whom.
    - **P5, flow ports.** The flow's typed ports show their type names; while dragging a connection, compatible ports are highlighted.
13. **Part 2a: running specs in the studio (R1–R4, User 2026-11-17).**
    - **R1, scope:**
      - **Preview runs:** a spec runs inside the studio. A chat panel shows live events over SSE (the running node is highlighted on the canvas, tool calls, text deltas, cost), with approvals in the chat and a stop button.
      - **Discovery:** model lists of Ollama and the other providers in the inspector, and the tools of an MCP server.
      - **API keys** for the providers, set in the studio and never shown again (only "set: yes/no").
    - **R2, no sign-in for now.** The studio stays local without login, bound to `127.0.0.1` by default. GitHub sign-in waits until the owner asks for it.
    - **R3, keys** are stored locally in `~/.config/grauwolf/studio/keys.json` (mode 0600); per-person storage in OpenBao comes with a sign-in.
    - **R4, limits:**
      - a budget per run (steps, tokens, time) with defaults that can be changed in the studio;
      - at most 2 concurrent runs;
      - `run_command` and writing tools only as the spec allows them (as with `spec run`);
      - runs in the studio process (decision 8).
14. **Agent kind on the agent node, no decision nodes in the overview (User 2026-11-18).**
    - **No decision nodes.** Decisions (`decide` nodes) are steps of the flow; they no longer appear in the overview. They are in the Flow tab.
    - **The agent kind on the agent node:**
      - **Agent** for a ready-made strategy (`single_run`, `react`, `chat`, `verified`);
      - **Graph-Agent** for an own graph;
      - **Planner-Agent** for an own graph with a planner node (`plan` or `goap`).
    - **Flow summary.** Graph and planner agents show a short summary of the flow, e.g. "Graph: 5 nodes, 1 decision" (also subgraphs and planners when present); clicking it opens the Flow tab.
    - **System One as a resource.** A `decide` node with `decider: system_one` makes the external decision service appear as a resource "System One (RKEV)" at the **Resources** port: an external service, like an MCP server. It is derived from the flow (not a separate spec section), so it cannot be disconnected or parked; its inspector names the decide nodes that use it and the variables `RKEV_BASE_URL`/`RKEV_API_KEY`.
15. **Planners in the flow view (User 2026-11-18).** The actions of a planner node (`goap`, `plan`) are not edges of the spec – the planner chooses them at run time. The flow view shows them anyway:
    1. **Dashed links** from the planner node to each action's subgraph or agent, labelled with the action name ("may run", not "always runs").
    2. **On the planner node:** the start state and the goals. Hovering an action shows its preconditions, effects and cost.
    3. **Expected plan (GOAP only):** the studio computes the plan for the start state with grauwolf's own GOAP planner and numbers the actions in that order (① ② ③); no valid plan is shown as a warning. An LLM planner (`plan`) has no expected plan.
    4. **In a run**, the actions light up in the order the planner actually chose, replanned steps included.
16. **The studio's layout: an IDE frame with a command palette (User 2026-11-18, chosen from design variants).**
    - **Left:** an activity bar (Explorer, Palette, Search) and next to it the active view: the explorer with the folder tree, the palette, or search over files and specs.
    - **Top:** tabs for open files (several at once, e.g. a spec and `add.rs`, unsaved marked with ●), and per spec tab the switch Overview / Flow / JSON. The JSON view is the spec source in Monaco.
    - **Right:** the inspector with its own tabs: Properties, Files (the files the selection refers to), JSON (the selection's JSON).
    - **Bottom:** a panel with tabs: RUN (chat and input), EVENTS (event lines such as `⇢ translator ✓ 1.1 s`, with a count), PROBLEMS (validation, with a count), TOOLS (tool calls of the run).
    - **Status bar:** valid or not, tool policy, lockfile, model backend reachable (e.g. Ollama).
    - **Command palette (⌘K / Ctrl+K)** over the canvas, e.g. "Add MCP server to Resources", "List tools…", "Go to node… (⌘P)", "Run with last input (⌘↵)".
17. **The studio as an MCP editor with live sync (M1–M5, User 2026-11-18).**
    - **M1, connection.** The studio serves MCP over Streamable HTTP at `/mcp`. A dialog "Connect a coding agent" shows the ready command to copy, e.g. `claude mcp add --transport http grauwolf-studio http://127.0.0.1:8090/mcp --header "Authorization: Bearer <token>"`.
    - **M2, protection without sign-in.** The studio creates a random MCP token at start, shown only in the studio; requests without it get `401`.
    - **M3, tools.**
      - Reading: `list_specs`, `read_spec`, `list_node_kinds`, `get_schema`, `validate`.
      - Editing the flow: `add_node`, `remove_node`, `connect`, `disconnect`, `set_params`, `set_field` (JSON pointer).
      - Editing the overview: `add_resource`, `remove_resource`, `move_node`.
      - Files: `create_spec`, `write_file`.
      - Running: `run_spec`, whose run also appears in the studio.
      - All tools work on the open workspace; a spec is named by path, defaulting to the active tab.
    - **M4, a shared working copy in the backend.**
      - The backend holds the unsaved working state of every open spec (spec and layout).
      - The browser and MCP clients change it through the same small operations with a version number, and the backend sends every change over SSE to all clients.
      - Concurrent edits are merged.
      - Save writes to disk.
      - The operations are invertible, which is the basis for undo/redo.
    - **M5, visibility.** Changes made by an MCP client briefly light up on the canvas, and EVENTS shows a line per operation (e.g. "claude-code · add_node ask (llm_request)").
18. **Undo and redo (User 2026-11-18).**
    - **Own changes only.** ⌘Z/Ctrl+Z takes back the user's own changes; ⇧⌘Z/Ctrl+Y redoes them. Changes made by an MCP client stay. Each MCP line in EVENTS has its own "Undo" that takes back exactly that batch.
    - **One action, one step:** dragging a node, connecting, adding or removing a resource, converting to a graph, and so on. Typing in a field is grouped until a pause of about 1 s or leaving the field.
    - **Building on the inverse operations** of decision 17. An undo is a new batch sent to the working copy, so other clients see it like any change; if the target has changed meanwhile, the step is dropped with a note.
    - **Per document,** kept across saves, cleared by a revert or a reload from disk.
19. **Flow layout with ELK (User 2026-11-18).**
    - **Layout engine:** the flow view (and the overview) is laid out with the Eclipse Layout Kernel (`elkjs`) instead of the studio's own layered layout and edge routing. ELK provides layers with crossing minimisation, orthogonal edge routing around nodes, label placement without overlaps, and subgraphs as nested groups.
    - **Edges:** orthogonal with rounded corners.
    - **When it runs:** automatically only for nodes without a saved position, as before. A command "Tidy up" (toolbar button and command palette) lays out the whole view anew; it is one undoable step.
20. **A menu bar over the canvas, as in the AgentModler (User 2026-11-19).**
    - Over the canvas of the Workspace tab and of a spec's overview: **+ Agent ▾** (new spec, a workspace spec as local sub-agent, A2A agent), **+ Tools ▾** (tool, tool file, built-in groups, tool packages of the catalog), **+ Resources ▾** (MCP server, knowledge, long-term memory, skills) and **Harness ▾** (New harness, Generate all, every harness with its publish state – a click selects it for the inspector). Over the flow: **+ LLM ▾**, **+ Tools ▾**, **+ Flow ▾** (the node kinds of the catalog by group). An entry adds at the place the palette's click uses (next to the selected agent, in the frame of the selected spec, in view).
    - The **palette stays** in the side bar for dragging to a place (owner's decision); the side bar view **Harnesses** goes (its parts are in the Harness menu and the workspace canvas).
    - A **⚙ Settings ▾** menu in the header holds GitHub…, Kubernetes… and API keys…, in place of the buttons spread over the studio.

## Consequences
- **One stack and one model.** The spec is the canvas's file format, so what the studio shows is what grauwolf runs.
- **One repository, one CI.** The API and the frontend change in the same commit. The architecture check applies to the studio crate (an app crate: it may compose adapters).
- **Next.js server features are not available.** The frontend must work as a static export.
- **Frontend tests and tooling.** The repo gains a Node toolchain for `studio/web/`. The development container needs Node, and CI needs a frontend job.
- **AgentWeaver workspaces must be converted.** Existing AgentWeaver workspaces (Kotlin projects) are not opened by the studio. Conversion of their graph JSON into specs is a possible later tool.

## Implementation notes (2026-11-17, part 1)
- **Frontend copy (Q7 a):** `agentweaver/frontend` was copied to `studio/web/` in a commit of its own, without `node_modules`, build output, `.env` files and history. Removed since: the export, review, build and runtime views, the code explorer of generated Kotlin projects and the AgentWeaver canvas with its property panels. GitHub workspaces, the preview chat, the MCP editor sync, API keys and discovery stay in the code, not mounted, and show as disabled "coming in part 2" in the toolbar and the preview panel.
- **Backend (Q3, Q11 a):** the app crate `crates/apps/grauwolf-studio`, binary `grauwolf-studio serve [--addr 127.0.0.1:8090] [--workspace <dir>] [--web <static export>]`; axum; the architecture check knows it as `arch::STUDIO` (may use host and server, nothing depends on it). API v1: `GET /specs`, `GET`/`PUT /specs/{path}` (atomic writes, paths kept inside the workspace), `POST /specs/validate` (problems with JSON pointer and the node, edge index and subgraph they belong to), `POST /specs/diagram`, `GET /schema`, `GET /node-kinds`; one error shape `{ error: { code, message } }`. The OpenAPI description comes from utoipa (`GET /api/v1/openapi.json`, `grauwolf-studio openapi`).
- **Palette from the catalog (ADR-0018):** node kinds and conditions now carry a `description()`; the kinds outside the catalogs are listed in `grauwolf_spec::STRUCTURAL_NODE_KINDS` / `STRUCTURAL_CONDITION_KINDS`. Ports are the signature with the example parameters.
- **Generated client:** `studio/web/lib/api/` from the OpenAPI JSON with openapi-typescript and openapi-fetch (pinned); a Rust test keeps `openapi.json` current, `npm run check-api` the generated types.
- **Canvas on spec JSON (Q2, Q8 b):** the frontend keeps the spec as raw JSON; canvas nodes are graph nodes (subgraphs as groups), connections are edges. A new edge gets the condition that turns the source's type into the target's. Layout `<stem>.layout.json`, version 1 (`nodes`, `subgraphs`, `viewport`, `collapsed`). Specs without a layout, or with nodes missing in it, get a layered left-to-right layout without overlaps; saved positions stay, the next save writes all.
- **Not yet:** sub-agent type checks and local skill folders are checked only by `grauwolf spec validate`; a spec with `strategy` is shown without graph.

## Implementation notes (2026-11-17, part 1b)
- **Owner's findings in a browser:** a `single_run` spec showed only `start` and `finish`, edges of graph specs were missing, and connections could not be dragged. Causes: the canvas syncs ran concurrently when a spec opened, and the Rete connection events of one sync edited the spec (edges duplicated or removed); the socket view's negative margins gave the socket element zero width, so the connection plugin never found a socket under the pointer and a drag moved the node. Fixed: syncs run one after another, the canvas changes the spec only through the store (the bidirectional connection flow calls `connect`; edges are deleted with Delete, the context menu or the inspector), sockets have their real size. `studio/web/e2e/studio.e2e.cjs` checks this in headless Chromium.
- **Two levels (owner's decision):** the **overview** shows the agent node and its resources (tools, tool files and folder, tool packages, built-in tool groups from `/node-kinds` `builtin_groups`, MCP servers, agent tools, knowledge, long-term memory, skills, self tools, `decide` nodes / System One), each tied to its part of the spec by a JSON pointer and edited in the inspector; the palette adds resources from templates. The **flow** is the editable graph, or for a `strategy` the flow grauwolf derives, read only. Tabs and a double click on the agent switch between them.
- **Flow endpoint:** `POST /api/v1/specs/flow` returns the main graph with `derived`, the types a strategy adds and `converted`, the spec with the strategy replaced by that graph and those types. It uses grauwolf's loader (`AgentSpec::from_json` → `grauwolf_strategies::expand`), no copy of the templates; the converted spec loads to the same agent, which `tests/flow.rs` checks for every strategy example. All four strategies have an exact equivalent, so "Convert to graph" is offered for each.
- **Layout:** an optional `overview: { nodes, viewport }` was added to the layout file within `layout_version: 1` (additive; older layouts stay valid). The derived flow of a strategy is laid out anew and not saved.

## Implementation notes (2026-11-17, part 1c)
- **Key order:** `GET`/`PUT /specs/{path}` and the `converted` spec of `/specs/flow` keep the order of the spec's keys (`converted` puts `graph` where `strategy` was). The studio reads and writes spec files with its own order-keeping JSON value (`ordered::OrderedJson`) and converts to `serde_json::Value` only for grauwolf's loader. serde_json's feature `preserve_order` was checked and rejected: no crate of the workspace enables it today, and Cargo unifies features over everything built together, so enabling it in the studio would switch every grauwolf crate in a workspace build (`cargo xtask check --full`, `cargo build --workspace`) to insertion-ordered maps – a change of iteration order for `types`, `mcp_servers`, lockfile entries and generated code that would then differ between a workspace build and a build of a single program.
- **File API (decision 10):** `GET /files` (the tree: path, `file`/`dir`, size, role `spec`, `layout`, `tool_code`, `skill`, `knowledge`, `other`; hidden entries, `node_modules`, `target` skipped; files specs refer to get the role of the reference), `GET /files/{path}` (UTF-8 text up to 1 MiB with media type; `415 binary_file`, `413 file_too_large`), `PUT /files/{path}` (atomic, folders created; specs may be written as text), `POST /files/{path}:rename` (the layout of a spec moves with it; `409 already_exists`), `POST /files/{path}:mkdir`, `DELETE /files/{path}` (a folder only with `recursive=true`). The path rules of the specs plus no hidden segment.
- **References:** `POST /specs/references` lists the files a spec refers to with pointer, workspace path, existence and template. They come from `grauwolf_agent_tree::file_references`, which walks the spec with the same code as the reader's `resolve_file_references` (one walk, two visitors: inline or record) and, if the spec loads with missing code taken as empty, adds `tools_dir`, local sub-agents and `grauwolf_generator::companions` – the companion paths of an image, now with the JSON pointer and kind of each field. No list of fields in the studio.
- **Templates:** `POST /specs/template` makes the missing file at a pointer: the body of a tool for its declared `args`, of `fn run`/`fn check`/`fn transform` for the types of a graph, a `SKILL.md`, a knowledge document. The frontend writes it with `PUT /files`. A slow test builds every template's code with `grauwolf-toolbuild`; the spec validates right after.
- **Frontend:** the spec list became a file tree (new spec, file, folder; rename; delete), other files open in Monaco as a second tab beside the canvas (Ctrl/Cmd+S, unsaved marker). Monaco comes from the studio itself (`public/monaco`, copied from `node_modules/monaco-editor` before `dev` and `build`), not from a CDN. The inspector lists the files of the selection with Open and Create from template; the validation offers the template for a missing file. The owner's example "03-tools.json" is `03-tool-files.json` among the examples; the e2e check follows its `code_file` to `03-tools/add.rs`.
- **Edge labels:** labels are placed along the edge where they cover no node and no other label (short edges first, then shifted just above or below the curve), drawn horizontally on a background above all connections; the auto-layout leaves 140 px between layers, and a flow is fitted into view but not below zoom 0.7. An edge that runs straight behind a node of the same row is still hard to follow; a layout that routes around nodes is left for later.

## Implementation notes (2026-11-17, part 1d)

- **Owner's decision:** the Flow tab exists only for a spec with a `graph` of its own. A spec with a `strategy` shows it on the agent node and in the inspector with "Edit as graph" (the `converted` spec of `POST /specs/flow` is written into the spec, unsaved, and the Flow tab appears) and "Show flow" (the derived flow in a read-only dialog, drawn by the same code as the flow view, with a note on the strategy and "Edit as graph"). A double click on the agent opens no flow for such a spec. The read-only "derived" mode of the flow view is gone; the dialog is its only renderer.
- **File tree:** `layout` files are not shown (they belong to their spec and are renamed and deleted with it); the API still lists them.
- **Monaco:** if `/monaco/vs/loader.js` cannot be fetched, the editor area shows a message instead of an unhandled rejection.

## Implementation notes (2026-11-17, part 1e)

- **Workspaces (decision 11):** `workspaces.rs` in the studio crate. `serve --root <dir>` (default `~/grauwolf-studio/workspaces`): own workspaces are the root's subfolders with `.grauwolf-studio/workspace.json` (`{ id, name, description?, created, source: { kind: "local" } }`), id = folder name; registered folders are listed in `<root>/.registry.json` (chosen over `<root>/../registry.json` so the root folder holds everything, as W1 says), their metadata kept there and nothing written into them. Ids are slugs of the name, made unique with `-2`, `-3` …, stored, so they survive restarts and renames. `serve --workspace <dir>` stays as single-workspace mode (id = slug of the folder name; creating, registering, renaming and deleting are `409 single_workspace`).
- **API (W2):** `GET`/`POST /workspaces` (templates `empty` – `agent.json`, a valid `single_run` spec –, `examples`, `copy`), `POST /workspaces:register`, `GET`/`PATCH`/`DELETE /workspaces/{id}` (an own workspace only with `?confirm=<id>`, then with its folder; a registered one leaves the registry only). The specs and files routes moved to `/workspaces/{id}/…` (`404 workspace_not_found`); `schema`, `node-kinds` and `openapi.json` stayed at the top. Register refuses the root, anything inside or around it and overlaps with any workspace, so no two workspaces see each other's files. The template `examples` copies `--examples <dir>`, by default the repository's `docs/user-guide/examples` if the binary still finds it; without it the template is refused (`no_examples`) and offered disabled.
- **UI (W3):** a start page without an open workspace (list with kind, spec count and path; New workspace, Register folder, rename, delete with the typed id), the workspace in the URL as `?w=<id>` (an unknown id falls back to the start page with a note), a switcher at the top left with the recently opened workspaces (localStorage); switching asks about unsaved changes. The header shows whether `grauwolf.toml` and `grauwolf.lock` exist (W5, read only).
- **Transition (W7):** `scripts/studio.sh` starts on the root folder; once it registers `~/grauwolf-studio-workspace` as "examples", and with no workspace at all it creates "examples" from the template. Example files are still added only to folders the script seeded (`.grauwolf-studio-seeded`), never overwriting one.

## Implementation notes (2026-11-17, part 1f)

## Implementation notes (2026-11-18, decision 17)

- **Working copy (M4):** `documents.rs` keeps one document per workspace and spec path – `{ spec, layout }` (the spec as `OrderedJson`, the layout as stored or `null`), a version, the file's content for `dirty` (compared without key order, so a value changed back is clean again) and the modification time and size of spec and layout file. `POST …/documents/{path}:open`, `…/ops` (`{ base_version, ops, client_id }`), `:save` (optional `force`), `:revert`, and `GET …/documents/events` (SSE: `ops` with version, ops, inverse, client, origin `studio`|`mcp:<name>`, dirty, conflicts, and from MCP tools a label and a highlight; `saved`, `reverted`, `disk_changed`, `closed`, `clients`, `files`, `run`, `resync`). `GET`/`PUT /specs/{path}` stay and work on the file; the editor no longer uses them.
- **Ops (M4):** `ops.rs` (pure; the frontend has the same model in `lib/doc-ops.ts`): `set` (with `at` for the place of a new object member), `insert`, `remove`, `move` (a rename in place within one object) on JSON pointers below `/spec` and `/layout`. `apply` returns the inverse ops – a removed member comes back at its place –, `apply_all` is all or nothing, `compose` joins batches, `diff` gives the ops between two states (lists by common prefix and suffix, item by item when changed in place, else a longest common subsequence). The MCP tools describe their edits as primitive ops (no higher-level op kinds): an `add_node` is one `insert`, a `remove_node` the removes of its edges, its node and its position – so every batch has an exact inverse and the browser can apply it without knowing the tool. Undo/redo is not built here (see the notes for decision 18); the inverses come with every answer and event.
- **Conflict rules (the brief's "simple rules"):** a batch is rebased over the batches of *other* clients applied after its `base_version` (a client's own earlier batches are not concurrent – it wrote on top of them, so the browser need not wait for an answer before the next batch; it still sends one at a time and joins the edits made meanwhile). Indices shift through inserts and removes in the same list; an op whose target was removed meanwhile is dropped; an op on the same pointer as a concurrent `set`, removed member or move – or on a pointer inside or around it – is applied and wins (last writer). Both are reported as `conflicts` (index, pointer, `overwrote`|`dropped`, the other origin) to the sender and in the event; the studio shows them as a message. Batches older than the last load or revert, or than the 1000 kept, are `409 stale_base` (open again).
- **Disk changes:** every open, batch and save compares the files' modification time and size with the document's: a clean document follows the file (`reverted`, origin `disk`), a dirty one is marked `disk_changed` and its save is `409 disk_changed` until it is reverted or saved with `force` (the studio asks). `PUT /specs`, the file routes and the MCP file tools tell the documents what they wrote, renamed or deleted.
- **Frontend on the working copy:** `store/documentStore.ts` holds a mirror per open document (`lib/doc-mirror.ts`: confirmed state, pending local batches, `local` = what is shown; remote batches rebase the pending ones; batches that arrive ahead of a missing version wait). The spec store's actions are unchanged: a subscription diffs each change of spec and layout against the mirror and sends the ops (the layout only when the canvas changed it – the document's layout may lack positions the canvas computed, `lib/doc-layout.ts` completes it from what the canvas shows). Remote changes set spec and layout without touching the selection; the JSON view merges them into its text and keeps the user's own edits (`rebasedText`, `mergeEdited`). Dirty marks come from the mirror; Save and Revert go to the backend; closing a dirty tab reverts the document; tabs, per-spec runs, validation (on the working copy), PROBLEMS, flow, planner view and parking work as before.
- **MCP endpoint (M1–M3):** `POST /mcp` on the studio's address, Streamable HTTP with grauwolf's own server side (`grauwolf_mcp::McpServer::handle`, built per request with the session's tools as `grauwolf-server`'s agent endpoint does) behind `grauwolf_server::with_token`. ## Implementation notes (2026-11-18, decision 18)

- **Model:** `studio/web/lib/undo.ts` (pure): per document an undo and a redo stack of steps, each a label ("Move node ask", "Connect draft → ask", "Add MCP server files", "Edit system_prompt") and the inverse ops of one user action against the document as the browser shows it (the mirror's `local`); bounded to 200 per stack, a new own action clears the redo stack. `store/documentStore.ts` keeps the histories; the spec store's actions name their change (`asEdit`), and the subscription that turns a change into ops computes its inverse (the layout back to what the canvas showed). No backend change.
- **One action, one step:** edits of the same group merge into the top step until it is sealed or its window passes – fields 1 s (`field:<pointer>`, params, edge), a drag and the JSON view until sealed; the shell seals on every `focusout` and `pointerup`, the JSON view applies a waiting edit before it seals on blur. Every action is one store call, so Convert to graph and connecting with its suggested condition are one step without action ids.
- **Undo/redo:** the step's ops are applied as a local edit and sent as a new batch based on the current version; the difference back (computed from the mirror like the backend's inverse, so it is ready at once) becomes the redo step, and vice versa.
- **Rebasing the stored inverses (the chosen approach):** the backend rebases a batch only over other clients' batches after its base and never over the sender's own, so a step sent with an old `base_version` would miss the user's later edits. Instead the browser keeps every stored inverse written against the current document: each change of `local` that is not a step (a remote batch, an own batch the backend rebased or refused, an EVENTS undo, Save's layout completion) is turned into ops (`diff` before/after) and rebased into the stacks from the top down – the step over the change, the change over the step, then on to the next step. Own actions need no rebasing (last in, first out). A step whose target a remote change overwrote or removed is marked with that origin; its undo shows "Could not undo '<label>': changed by <origin>" and drops the step. Ops that no longer apply, or conflicts in the backend's answer to an undo batch, give the same note; the document stays as the backend applied it.
- **Own changes only:** remote batches never become steps. Each EVENTS line of an MCP batch keeps the event's `inverse` (rebased over the pending local batches, then over every later change; a later change of its target – the user's included – marks it) and offers **Undo**, which sends it as a local edit outside the user's stacks; the line then shows "undone" (or "not undone: changed since").
- **Lifetime:** per document, kept across Save; cleared by Revert, a reload from disk (`reverted`), `stale_base` (the document is opened again), closing the tab, and a page reload.
- **UI:** Ctrl/⌘+Z undo, Ctrl+Shift+Z/⇧⌘Z and Ctrl+Y redo as commands of the registry (`alternatives` for the second shortcut) – in a text field and in Monaco the field's own undo applies; Undo and Redo buttons in the header with the step in the tooltip ("Undo Move node ask"); the palette commands *Undo* and *Redo*; the inspector's forms remount after an undo (`revision`).
- **Tests:** vitest for the model (`lib/undo.test.ts`: undo/redo, drag and typing merge, other fields, redo cleared, remote changes rebased and kept, conflicts by overwrite and removal, rebasing down the stack, own non-steps, bounds), the batch marks in `lib/doc-mirror.test.ts` and `matchesCommand`; the owner-approved Playwright scenarios (`undoChecks`, `E2E_ONLY=undo`, also in the full run): drag with Ctrl+Z and Ctrl+Shift+Z, a connection, a palette resource and its connection, typing in `system_prompt`, an MCP node that Ctrl+Z leaves and EVENTS Undo removes, a move undone while the client set the node's params, undo after Save. The flow is laid out in two ELK passes instead: every graph on its own, then the graphs as compound boxes (room for frame and title) top to bottom, the planners' links as edges of that pass from the planner to the top of its action subgraphs – so the action subgraphs stand in a row below their planner as decision 15 wanted –, the other subgraphs chained one below the other. The links are layout-only edges with ELK routes and label places; they stay drawing, not spec.
- **When it runs:** `completeLayout` places only nodes without a saved position – all of a new spec at ELK's places, single new nodes moved along with the saved node nearest to them in ELK's arrangement and never onto another node; the store awaits it on open, create, *Edit as graph* and Save and runs it after other changes (an MCP client's or the JSON view's new node) outside the undo history. *Tidy up* (`tidyUp`: a button beside the view switch, the command palette, ⇧⌥F) lays out the shown flow or overview anew as one undo step ("Tidy up") and fits the view.
- **Routes and fixed positions:** routes are never saved. On every draw `drawingRoutes` asks for ELK's arrangement of the drawing (kept in memory per graph shape) and gives each edge ELK's route where both ends stand where ELK put them (up to a common offset) and route and label meet no node or label. ELK cannot route around nodes it did not place (`layered` moves them, `fixed` routes nothing), so every other edge – a dragged node's – is routed by `routeAround`: out of the port, over a grid of lines that keep 16 px from every node and from other subgraphs' frames, Dijkstra with a cost per bend, into the port; its label on a free stretch. Edges are drawn with 8 px rounded corners, their ends moved to the sockets Rete measured; subgraph frames grow around their edges' routes. The old layered layout (`autoLayout`, `completeLayout` of `spec-canvas.ts`, `actionRowSubgraphs`), the label places on Rete's curve (`edge-labels.ts`) and the detours (`edge-routing.ts`) are gone.
- **Fit:** the nodes, frames, routes and labels, centred, at most zoom 1, at least 0.6 (`MIN_FIT_ZOOM`, before 0.7) – a wider flow starts at its left end and scrolls; the run's fits are readable too.
- **Tests:** vitest for the ELK input (sizes, ports, labels, subgraphs, links, the overview's group ports), the mapping of the result to positions and routes, placing missing nodes, the planner row and the stacked subgraphs, Tidy up, frames around their routes, routing around a moved node, the router, label places, snapped ends and rounded paths, the Alt shortcut by key code, and for `04-tool-loop`, `04-decide`, `06-subgraph` and `06-goap` no route through a node box and no label on a node or another label. The owner-approved Playwright layout cases (`layoutChecks`, `E2E_ONLY=layout`) check the same in the browser's own geometry for copies without a layout file of the four flows and of `08-coordinator`'s overview, the zoom after the fit, a drag with the edges going around, Tidy up as one undo step and ⌘Z restoring the dragged position; screenshots `layout-04-tool-loop.png`, `layout-04-decide.png`, `layout-06-subgraph.png`, `layout-06-goap.png`, `layout-overview.png`.
