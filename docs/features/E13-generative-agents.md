# E13 – Generative agents (JSON DSL → GraphAgent)

Core feature of grauwolf.

**Idea:** An agent is described completely as a **JSON document** (model, prompt, tools including tool code, graph of
nodes/edges/subgraphs, features). A runnable GraphAgent is created from this document. The JSON can be written by
humans or **generated by an LLM** (a "builder agent" creates agents).

```
Description in natural language
        │  (optional) builder agent, structured output against the DSL's JSON schema
        ▼
  AgentSpec (JSON) ── validation (schema + semantics: graph, types, tool references)
        │
        ├──► Mode A: codegen   → Rust crate (Cargo.toml, main.rs, tools.rs, graph.rs)
        │                        → formatted → `cargo check` → errors back to the LLM (repair loop)
        │
        └──► Mode B: interpreter → GraphAgent directly at runtime, without compiling
```

## Features

| ID | Feature | Rust approach | Prio |
|----|---------|-------------|------|
| F13.1 | **AgentSpec data model** (name, version, model/provider, system prompt, params, tools, graph, features) | serde structs in crate `grauwolf-spec`; versioned format (`"spec_version": 1`) | M1 |
| F13.2 | **JSON schema of the DSL** – so that an LLM can generate valid specs via structured output | `schemars` on `AgentSpec` | M1 |
| F13.3 | **Graph spec**: nodes (predefined: `llm_request`, `execute_tool`, `llm_send_tool_result`, … / custom with code), edges with conditions (`on_tool_call`, `on_assistant_message`, `on_condition` with expression), `transformed`, subgraphs with a tool subset, start/finish | Enum `NodeSpec`, `EdgeSpec`, `ConditionSpec` | M1 |
| F13.4 | **Tool spec**: name, description, argument schema (→ generated `struct Args`), return type and **implementation** | `ToolImpl` enum: `RustCode { body }`, `Builtin { name }`, `Http { method, url_template, … }`, `Mcp { server, tool }` | M1 |
| F13.5 | **Semantic validation**: edge types match, all nodes reachable, finish reachable, tool references exist, names are valid Rust identifiers | Own validation layer with precise error paths (JSON pointer) – errors are phrased so an LLM can act on them | M1 |
| F13.6 | **Mode A – codegen**: spec → Rust source code that uses the typed builder API (E05) | Builder-based code generation (see "Codegen library") | M1 |
| F13.7 | Project generator: complete crate (Cargo.toml with matching `grauwolf` features, `main.rs`, modules) | File writer + templates for Cargo.toml – ✅ ADR-0084: feature `app` with `run_app` (facade only with the required features), automatic memory via `run_with_memory` | M1 |
| F13.8 | Formatting and syntax check of the generated code | `syn::parse_file` (syntax) + `prettyplease` (formatting, without external rustfmt) | M1 |
| F13.9 | **Compile check & repair loop**: `cargo check --message-format=json`, map errors back to spec elements, LLM corrects spec/tool code | `tokio::process`, diagnostic mapping via comment markers in the generated code | M2 |
| F13.10 | **Mode B – interpreter**: spec → GraphAgent at runtime; node data as `serde_json::Value` (ADR-0010, ADR-0017); tool code is built into artifacts beforehand via `grauwolf spec build` (ADR-0024) | Runtime builder on the same graph engine | M1 |
| F13.11 | **Tool sandbox**: Rust tool code is compiled to a WASM component (`wasm32-wasip2`) in **both modes** and executed in `wasmtime` | Capabilities from the spec (e.g. allowed HTTP hosts via wasi-http, otherwise no FS/network), fuel/memory limits, timeout; the interpreter loads the same components | M1 |
| F13.12 | **Builder agent**: predefined agent that creates an AgentSpec from request text, validates, generates and repairs it | Its own GraphAgent (dogfooding), uses F13.2/F13.5/F13.9 | M2 – ✅ implemented (`grauwolf-builder-agent`, `grauwolf spec create`, ADR-0035) |
| F13.13 | Round trip: load an existing spec, change it, regenerate; diff of the generated code | The spec is the source of truth; generated code with header "generated – do not edit" + escape hatches (`custom.rs`, which is never overwritten) | M2 |
| F13.14 | Visualization of the spec (Mermaid) | same function as F05.16 | M2 |
| F13.15 | **Security**: LLM-generated tool code runs only in the sandbox (F13.11) | Additionally an allowlist of permitted crates in tool code; the build of the tool components is also isolated (own target dir, no build.rs/proc macros from third-party crates) | M1 |

## Example spec (draft)

```json
{
  "spec_version": 1,
  "name": "calculator",
  "model": { "provider": "openai", "id": "gpt-4o" },
  "system_prompt": "You are a calculator. Use tools for every arithmetic operation.",
  "input": "string",
  "output": "string",
  "tools": [
    {
      "name": "add",
      "description": "Adds two numbers",
      "args": { "type": "object", "properties": { "a": { "type": "number" }, "b": { "type": "number" } }, "required": ["a", "b"] },
      "returns": "number",
      "impl": { "kind": "rust_code", "body": "Ok(args.a + args.b)" }
    }
  ],
  "graph": {
    "nodes": [
      { "id": "call_llm",    "kind": "llm_request" },
      { "id": "exec_tool",   "kind": "execute_tool" },
      { "id": "send_result", "kind": "llm_send_tool_result" }
    ],
    "edges": [
      { "from": "start",       "to": "call_llm" },
      { "from": "call_llm",    "to": "finish",      "when": "on_assistant_message" },
      { "from": "call_llm",    "to": "exec_tool",   "when": "on_tool_call" },
      { "from": "exec_tool",   "to": "send_result" },
      { "from": "send_result", "to": "exec_tool",   "when": "on_tool_call" },
      { "from": "send_result", "to": "finish",      "when": "on_assistant_message" }
    ]
  }
}
```

## Codegen library

Proposal by the user: [`codegen`](https://github.com/carllerche/codegen) (MIT, current version 0.3.0), to be improved as needed.

**What `codegen` does well:** builder API for items: `Scope`, `Module`, `Struct`, `Enum`, `Trait`, `Impl`, `Function`, `Block`, `Field`, `Import`, generics/bounds, derives, doc comments. This fits well with a mapping from JSON → items.

**Limitations (room for improvement):**
1. Function bodies and expressions are **plain strings** (`line("...")`); there is no syntax check.
2. Only basic formatting; without `rustfmt` the code is hard to read.
3. Gaps in items and syntax, e.g. `const`/`static`, type aliases, macro invocations, `#[attr]` at all levels, closures.
4. No mapping of generated lines back to their source, which the repair loop (F13.9) requires.
5. Hardly maintained any more (open PRs stay open).

**Options:**

| Option | Description | Assessment |
|--------|-------------|------------|
| A | `codegen` as a dependency + own extension layer | fast, but limitations 1–4 remain |
| B | **Fork as `grauwolf-codegen`** (MIT permits this), improved with: validation of every code string via `syn`, formatting via `prettyplease`, missing items, source map (spec path → lines) | ✅ **Decided (2026-11-06)** |
| C | Instead, `quote` + `syn` + `prettyplease` (ecosystem standard for proc macros) | maximally robust and type-safe, but token streams make the mapping JSON → code more cumbersome and come without a builder |

The improvements from option B can later be offered upstream.

## Decisions (2026-11-06)
- Codegen: fork `grauwolf-codegen` (option B).
- Both modes (codegen **and** interpreter) belong to M1.
- Tool code runs directly in a sandbox (WASM component + wasmtime), in both modes.
- Approach: **vertical slices, spec-first** – order and content only in [../architecture.md](../architecture.md), section 5.

## Clarifications from review iteration 1
- Strict deserialization, `kind` as a string checked against the catalog, conditions as objects, namespaces, reserved IDs, versioning: ADR-0025.
- Nominal types in the `types` section: ADR-0022. Edge conditions: ADR-0021.
- Custom nodes only as WASM transformations `Value → Value` or compositions: ADR-0028.
- Tool build as its own step with an artifact cache (`grauwolf-toolbuild`): ADR-0024.
- The example above still shows `"when"` as a string; per ADR-0021 it becomes an object (`{ "kind": "on_tool_call" }`).
