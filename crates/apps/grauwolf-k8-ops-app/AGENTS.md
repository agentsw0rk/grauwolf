# grauwolf-k8-ops-app

**Layer:** `apps` · **Status:** ADR-0120, stages 1 and 2. The operator program that sets up SPIRE and OpenBao for agents on Kubernetes: binary `grauwolf-k8-ops` (`src/main.rs`) on the library `grauwolf_k8_ops_app`. Commands: `doctor [--json]`, `oidc install`, `openbao setup|token [--ttl 8h] [--renewable]`, `agent add|list|remove|check|build|deploy|status|logs|undeploy|allow|deny|callers`, `secret set|get|list|delete`, `build secret registry <name> --server S --username U [--namespace NS]` and `build secret git <name> --username U [--namespace NS]` (ADR-0129 B4), `trust-domain set <domain> [--apply --yes --backup FILE --consumers FILE --from DOMAIN --timeout SECONDS]`, `trust-domain restore <backup> [--apply --yes --backup FILE --timeout SECONDS]`, `identity install|status|uninstall|allow|deny` (ADR-0111). The trust domain is read in one function, `spire::trust_domain`; `spire::trust_domain_sources` lists every place that holds one.

`agent deploy --harness <file>` (ADR-0128 decision 6, `src/harness.rs`): the settings come from the harness file instead of flags – the agent's name (the positional name is then refused) `image` (`--image` is then optional; without both the default `Harness::default_image` with `grauwolf_agent_tree::harness_registry` – `[harness] registry` of the nearest `grauwolf.toml` – and this program's version, ADR-0128 H7; without a registry either: `no image: …`) `port` (else `DEFAULT_PORT` 8080) and `env` (as `NAME=VALUE` through the checks of `--env`); a flag for a setting the harness file sets is refused (`one_source`: `--image: the harness file sets `image` already; …`), before anything is written; errors `<file>:<pointer>: …`.

`agent build --harness <file> [--project DIR] [--namespace NS] [--kaniko-image IMAGE] [--registry-secret NAME] [--git-secret NAME] [--timeout SECONDS]` (ADR-0129 B4, `src/build.rs`): the studio's build without the studio. The source is `grauwolf_git::build_source` of the project folder (default `build/<name>` of the working directory; its refusal is the error), the destination the harness's `image`, else `Harness::default_image` of `[harness] registry`, else `no image: …`; all of that is checked before the cluster is touched. It ensures the namespace `grauwolf-builds` (`grauwolf_k8s::BUILD_NAMESPACE`, label `app.kubernetes.io/managed-by: grauwolf-k8-ops`, deliberately without the restricted Pod Security level: Kaniko runs as root), runs the Kaniko Job (`grauwolf_k8s::run_build_with`, image `KANIKO_IMAGE`, timeout default 1800), `--registry-secret` / `--git-secret` name Secrets that must already exist in the build namespace (else the error `secret <name> not found in namespace …`, no Job is created), prints every log line as it comes and then `built and pushed <image>` (exit 0) or the failure/timeout line (exit 1).

`build secret registry|git` (`src/build.rs`) create or update, in the build namespace (made like `agent build` does), the Secret `agent build --registry-secret|--git-secret` uses: type `kubernetes.io/dockerconfigjson` (`grauwolf_k8s::registry_secret`) or `Opaque` with `username` and `password`. The token is read like a value of `secret set` (stdin or hidden prompt, never an argument) and appears in no output; the output is `secret <namespace>/<name>: created|updated|unchanged`.

## Purpose
The manual steps of the ADR-0110 live check (and `examples/spire-openbao/`) as repeatable commands: every command reads the state, changes only what differs and says `created`, `updated` or `unchanged` per object. `execute(command, &Services, &mut Io)` runs one command (tests use it with `grauwolf_k8s::testing::FakeCluster`); `run(args, &mut Io)` parses, connects (`Services::connect`: kubeconfig and `--context`, token from `--token-file` or `OPENBAO_TOKEN`) and executes. OpenBao is reached through the Kubernetes API service proxy (`ProxyTransport`) unless `--openbao-addr` is given (`HttpTransport`).

Modules: `egress` (`agent deploy --egress`, ADR-0110 stage 6: `derive`, `Resolver` (`Services.resolver`: `System` or a `Fixed` table for tests; an external name that resolves to the LoadBalancer IP or an external IP of a Service also gets a rule to that Service's pods, ADR-0111 live check), `plan` (an `any_port` destination: all pod ports of its Service; a pattern or a missing Service: the namespace without ports), `sync`, `remove`, `summary_of`; the NetworkPolicy `grauwolf-egress`, see the developer guide 9.6), `cli` (clap, `Settings` with the defaults of the cluster), `services` (transports, `Services`), `spire` (trust domain, server version, replicas), `hcl` (`trust_domain` extractor and rewriter, plugin blocks, federation detection; no HCL library), `x509` (SPIFFE trust domains of the CA certificates in a PEM bundle by a minimal DER walk), `consumers` (the `--consumers` TOML and the replacement rule), `trust_domain` (plan, backup, change, verification), `restore` (reads a backup, plan, change; reuses the steps of `trust_domain`), `oidc`, `openbao_setup`, `identity` (the identity service of ADR-0111 Q3/Q4: `install`, `status`, `uninstall`, `allow`, `deny`; its policy file parser), `agent` (names, desired objects, `add`/`list`/`remove`), `caller_spec` (the check of a spec's calls to other agents of the cluster: `auth.spiffe`, https on the mTLS port, permission), `callers` (`allow`, `deny`, `callers`: the ConfigMap `grauwolf-callers` and the NetworkPolicy `grauwolf-mtls-callers`; ADR-0109 Q7-Q9), `deploy` (`deploy`, `status`, `logs`, `undeploy`, the wait for rollout and `/health`; ADR-0121), `agent_files` (the agent tree as a ConfigMap with one `subPath` mount per file), `secret`, `check` (the Job), `doctor` (two sections, `prerequisites` and `setup`; one line per check with status, reason and the next step), `io` (`Io`: output, errors, stdin, optional hidden prompt).

## Allowed dependencies
- grauwolf crates: grauwolf-egress (the destinations of the spec tree), grauwolf-git (`build_source` of `agent build`: the commit, branch and remote of the project folder, refusing uncommitted or unpushed changes), grauwolf-config (only `VARIABLES`, to validate `--variable` and `--env`), grauwolf-k8s (the cluster), grauwolf-openbao (the OpenBao calls), grauwolf-agent-tree (`AgentTree::read` of `agent deploy --spec`; an adapter, so the layering allows it; it brings the tool build crates into the binary) and grauwolf-spec (`AgentSpecExt::code_pieces`); dev: grauwolf-k8s with feature `testing`, grauwolf-test, git2 (real temporary repositories for the `agent build` tests)
- **Never any other app crate** (host, server, CLI, facade, tools-app) and no app crate depends on this one: `cargo xtask check-arch` rejects it.
- External: clap, getrandom (the server token), rpassword (hidden prompt on a terminal), serde_json, toml (parse only), tokio (`rt-multi-thread`, `time`)

## Invariants
- A secret value comes from stdin or a hidden prompt, never from an argument or the environment, and appears in no output or error; errors name agent and key only. The one exception is `secret get <agent> <key> --reveal`: it prints the value to stdout and nothing else, and refuses without `--reveal`.
- An agent's namespace is only touched if it carries `grauwolf.io/agent=<name>` and `app.kubernetes.io/managed-by=grauwolf-k8-ops`; `agent add` refuses a namespace that exists without the label, `agent remove` never deletes one. `agent remove` also deletes the removed agent's entries (by `/ns/<ns>/sa/<name>`) from the `grauwolf-callers` of the other agents and fits their NetworkPolicies, so no entry dangles; it lists them before the confirmation and changes nothing if cancelled.
- One agent, one namespace (restricted Pod Security Standard enforced), one service account, one OpenBao role and policy `agent-<name>`; the role is bound to exactly `spiffe://<trust domain>/ns/<namespace>/sa/<name>`, the policy reads only `<kv>/data/agents/<name>/*`.
- `agent check` deletes its Job (propagation `Background`) on success, failure and timeout. It checks every mapped variable of the agent in one Job (`--variable`, repeatable, narrows it), prints the whole log and, for a `permission denied` of a read (not of a login), a hint with the agent's policy and the path that was tried.
- `trust-domain set` without `--apply` changes nothing. With `--apply` the backup file is written first (never overwritten; if it cannot be written nothing is changed), the SPIRE agents and the provider are restarted only after the bundle ConfigMap carries a CA of the new domain, a server data volume is only recreated while that CA still has the old domain, and it refuses a server whose data is not a SQLite file on a volume claim template, and federation. Consumers are rewritten only at `spiffe://<old>` IDs and the quoted value `"<old>"`, never at a bare substring.
- `trust-domain restore <backup>` accepts only a backup written by this tool (`tool` is `set` or `restore`, known `format`, `from` a valid trust domain) and restores `from`. It restores only the `data` of the ConfigMaps of the backup (never metadata, labels or annotations; a missing ConfigMap is refused by name), only the roles of agents that still exist (a removed agent does not get its role back), and restarts the SPIRE workloads and the consumer workloads of the backup. Without `--apply` it changes nothing; with it a backup of the current state (the same format, restorable again) is written first and nothing changes if that fails. Same order and refusals as `set`; the server data is only recreated while the CA lacks the restored domain; a state that already equals the backup is `already as in the backup, nothing to do` and writes no backup.
- `agent deploy` writes nothing before everything it can check is checked (agent, quantities, `--env`, the tree). A value of `--env` goes into the Deployment (not secret); a name mapped to OpenBao in the agent's `grauwolf.toml` is refused. The pod is restricted-PSS clean (numeric user 65532, seccomp `RuntimeDefault`, all capabilities dropped, no privilege escalation, no service account token), one replica with strategy `Recreate`. It always runs with `GRAUWOLF_SPIFFE=1`: the container port `mtls` (`--mtls-port`, 8443; also a Service port), `GRAUWOLF_SPIFFE_USERS=/etc/grauwolf/callers/callers.json` and `GRAUWOLF_SPIFFE_PUBLIC_URL=https://<name>.<ns>.svc:<mtls port>` (these four variables are reserved); `grauwolf-callers` is mounted as a directory (a `subPath` mount would not see the ConfigMap's updates), created as `{}` only if missing, never replaced, and left out of the pod hash so that callers apply without a restart; `deploy` also syncs the NetworkPolicy to its ports. The probes stay on the HTTP port. `--otel [--otel-endpoint URL, default http://lgtm.lgtm.svc:4318] [--otel-content]` adds `--otel`/`--otel-content` to the `spec serve` command (with `--spec`) or, for the generated service of an image (no `--spec`), `GRAUWOLF_OTEL=1` and with `--otel-content` `GRAUWOLF_OTEL_CONTENT=1` (ADR-0123), plus `OTEL_EXPORTER_OTLP_ENDPOINT` and `OTEL_SERVICE_NAME` (the agent's name) to the pod, so it is part of the hash and a deploy without `--otel` removes it; `--env` refuses those four names only with `--otel`; `--events` adds `--events` to the `spec serve` command (with `--spec`) or, for the generated service of an image, `GRAUWOLF_EVENTS=1` (ADR-0121): the events as JSON lines on stderr, so in the pod log; part of the pod hash, a deploy without `--events` removes it; `--env GRAUWOLF_EVENTS` is refused only with `--events`; `status` shows `events: on|off` (`events` in `--json`), `agent logs --events-only` prints only the lines that start with `{"event":`; `status` shows `tracing: on (<endpoint>)`/`off`, `doctor` the line `tracing` (the endpoint's Service must exist, the collector is never called). A hash of the pod, the configuration and the agent files is an annotation of the pod template: an unchanged deploy writes nothing. The server token (32 random bytes, hex) is created only if missing at `<kv>/agents/<name>/server-token`, mapped to `GRAUWOLF_SERVER_TOKEN`, kept by `undeploy` and redeploys, and printed only by `secret get --reveal`. `--spec` refuses what needs a build or a fetch (tools with code, graph code, tool packages, a `tools_dir` that holds tool files, git skills), a tree above about 1 MiB, a path of the spec that leaves the spec folder, and a `long_term_memory.store` or `knowledge.index` that has no folder of its own (see the writable folders below). `undeploy` keeps identity, role, secrets, the callers and (without `--purge-data`) the PVC.
- Writable folders (ADR-0121): `agent_files::writable_places` finds the relative `builtin_tools.root`, `tools_dir` and the folders of `long_term_memory.store` and `knowledge.index` (a local copy of the file itself is not shipped) of every node (lexically normalized; `..` out of the root spec's folder is refused, an absolute path only warns unless under `/data`) and `deploy` mounts `files/<path>` of the data volume there, made before the start by the init container `data-dirs`. A mount never hides spec files (root with files: stays read-only with a warning; `tools_dir` with files, a store or index in the spec's own folder or in a folder with spec files: refused with a hint).
- Callers (ADR-0109 Q7-Q9): `agent allow|deny` need both agents to exist (`deny` also removes the entries of an agent that is gone, by its name), write the ConfigMap `grauwolf-callers` (key `callers.json`, SPIFFE ID to user, sorted) and make the NetworkPolicy `grauwolf-mtls-callers` fit it: one rule for the HTTP port without `from` (anywhere), one for the mTLS port from the namespaces of the callers (`kubernetes.io/metadata.name`); with no callers the second rule is left out, because an ingress rule without `from` admits everybody. The ports are those of the Deployment's container (`http`, `mtls`), else 8080 and 8443. A policy that was changed by hand is patched back even though `ensure` would skip it.
- `caller_spec` reads the specs as JSON (`spec_version` objects among the files of the tree, in `deploy` from the files it stores, in `doctor` from the ConfigMap `grauwolf-agent`); `deploy` only warns. `doctor` has per agent the lines `callers`, `NetworkPolicy` and `caller spec` (an image deploy without a spec says that its calls are not checked) and, once a policy exists, one warning `NetworkPolicy enforcement`: the API cannot tell whether the network plugin enforces them, so the hint names a counter-check from a pod in a namespace that is not allowed.
- Least privilege in OpenBao: `openbao setup` also writes the policy `grauwolf-k8-ops` (`openbao_setup::rules`, a table of path and capabilities that follows `--jwt-mount` and `--kv-mount`; no `sys/*` wildcard, no token creation, nothing outside `<kv>/*/agents/*`; for the identity service `sys/mounts/transit`, `transit/keys/*`, the policy and the role `grauwolf-identity`, so `openbao setup` must run again after an update), and `openbao token` creates a token with only that policy (no `default`, `no_parent` if the token in use may, else a child) and prints it alone on stdout. Every OpenBao call of the tool must be covered by a rule: `tests/restricted_token.rs` runs the commands against a fake OpenBao that enforces the policy (`Env::restrict_to`), so a new call without a rule fails there. `doctor` warns (`OpenBao token policy`) while the token has the policy `root`.
- `--context <name>` (global) selects the kubeconfig context; `doctor` starts its text output with `Cluster <server> (context <name>)` (in `--json` the same is in the reason of the check `cluster`); the other commands do not print it, because their output is captured and pasted (decision 2026-11-15).
- Identity service (ADR-0111 Q3, Q4): `identity install --audience` is repeatable (joined with commas into `GRAUWOLF_IDENTITY_AUDIENCE`); `identity install` touches only namespace `identity` with the label `grauwolf.io/component=identity` (it refuses one without it) and no agent label, so it is never an agent. It writes OpenBao first (the mount `transit/`, the key `--transit-key` of type `ecdsa-p256`, created if missing and never replaced; the policy `grauwolf-identity` with `update transit/sign/<key>`, `read transit/keys/<key>` and the grants' KV folders; the JWT role `grauwolf-identity` bound to `spiffe://<td>/ns/identity/sa/grauwolf-identity`), then the ClusterSPIFFEID `grauwolf-identity` (namespace `identity`, pod label `grauwolf.io/agent=grauwolf-identity`), the service account (with `--pull-secret NAMESPACE/NAME` the secret is copied into `identity` by `agent::copy_pull_secret`, the same as `agent add|deploy`, and attached to it), the ConfigMap `grauwolf-identity-policy` (`policy.json`; replaced only by `--policy`, else made as `{"callers": {}}` if missing; mounted as a directory and not part of the pod hash, the service re-reads it), the Deployment (the CLI image running `grauwolf identity serve --port --mtls-port`, restricted-PSS clean like an agent, every setting as a `GRAUWOLF_IDENTITY_*` variable), the Service (`http`, `mtls`), the NetworkPolicy `grauwolf-identity-ingress` (HTTP port from anywhere, mTLS port from namespaces with `grauwolf.io/agent`) and the egress policy `grauwolf-egress` through `egress::plan` (DNS, OpenBao, the JWKS host or the issuer's host; the SPIRE agent is the CSI socket). The pod carries an agent pod's labels so that `deploy::wait_ready` and `egress::plan` apply. `uninstall` deletes namespace, ClusterSPIFFEID, role and policy and keeps the key unless `--delete-key` (which sets `deletion_allowed` first). `identity allow <agent> [--purpose …]` / `deny` edit the policy like `agent allow/deny` (agent must exist for `allow`; `deny` also removes the entries of a removed agent by name). Grants (ADR-0111 stage 3): `identity::Policy { callers, grant_agents, triggers }` mirrors the service's file (`grants.agents`, `grants.triggers`; the `grants` object is written only when not empty); `identity allow|deny <agent> --grants [--purpose …]` edits `grants.agents`, `identity allow|deny --trigger <schedule name or spiffe id>` edits `grants.triggers` (a name is `schedule::spiffe_id`, `spiffe://<td>/ns/schedules/sa/<name>`); `identity status` shows the section. `identity grants [--revoke <id>] [--json]` reads every grant from `<kv>/identity/grants/` (`Bao::kv_read`, never the tokens' data) and revokes one by deleting `<kv>/identity/grant-tokens/<id>`, then `<kv>/identity/grants/<id>`; the operator's policy (`openbao_setup::rules`) has read on the grants' data, list/read/delete on their metadata and read/delete on the tokens' metadata. The fake OpenBao of the tests keeps whole secrets in `kv_data` (`Env::store_grant`). `identity install --grant-client-id <id>` sets `GRAUWOLF_IDENTITY_GRANT_CLIENT_ID` and `GRAUWOLF_IDENTITY_GRANT_KV_MOUNT` (= `--kv-mount`); the OpenBao policy `grauwolf-identity` (`identity::openbao_policy(key, kv mount)`) always also has create/read/update on `<kv>/data/identity/{grants,grant-tokens}/*` and read/list/delete on their metadata. `doctor` has the line `identity service` (ok when not installed and no agent uses it). `agent deploy --identity` (ADR-0111 Q5) reads the identity Service (refused without `identity install`) and sets `GRAUWOLF_IDENTITY_URL` (`https://grauwolf-identity.identity.svc:<mtls port>`) and `GRAUWOLF_IDENTITY_SPIFFE_ID` (part of the pod hash; a deploy without the flag removes them; `--env` refuses both names always); SPIFFE is always on in a deployed agent, so the server's start error cannot happen. With `--egress` the identity service is a destination (its namespace, the mTLS pod port); its ingress side already admits every agent namespace. `agent status` shows `identity: on (<url>)|off` (`identity` in `--json`), `agent check` prints a `hint:` when the agent uses the service and it is missing or not ready (`identity::hint_for`), `doctor` fails the line `identity service` then.
- `--pull-secret` (`agent::copy_pull_secret`): a secret that already exists in the target namespace with the same `type` and `data` (e.g. cloned by Kyverno, which refuses writes to its labels) is reported `unchanged` and never written; it is still attached to the service account.
- `doctor` changes nothing; its exit code is 1 when a check fails (warnings do not count).

## Tests
- `tests/trust_domain.rs`: plan, refusals, the change in order, resume and timeouts (also of `restore`: plan, refusals, skipped roles, order, round trip, restore of a restore, no-op, resume), with a small simulation of the controllers (`FakeCluster::on_change`: a StatefulSet that scales, a server that writes a new CA when its volume is new).
- `tests/deploy.rs`: `agent deploy|status|logs|undeploy` (with the mTLS port, the callers directory, no restart when only callers change), `agent remove` with a deployed agent and the deployment lines of `doctor` (`FakeCluster::set_deployment_outcome` plays the Deployment controller; `Env::health` is the status of `/health` through the service proxy).
- `tests/build.rs`: `agent build --harness` against `FakeCluster` (`set_job_outcome`) and real git repositories made with git2: the Job's arguments, the namespace, the log, exit codes, refusals before any write, the default image, the existing and the missing Secrets and `build secret registry|git` (the token only from stdin, never printed).
- `tests/caller_spec.rs`: the warnings of `deploy` and the callers lines of `doctor`.
- `tests/callers.rs`: `agent allow|deny|callers` (repeat runs, `--as`, unknown agents, the content of the NetworkPolicy) and the clean-up of `agent remove`.
- `tests/identity.rs`: `identity install|status|uninstall|allow|deny`, `agent deploy --identity` (variables, status, egress, the hint of `check`), the doctor line and the restricted policy.
- `tests/commands.rs`, `tests/doctor.rs`: against `FakeCluster` (in-memory API server) with a small fake OpenBao behind its service proxy (`tests/common/mod.rs`); `tests/binary.rs` starts the real binary.
