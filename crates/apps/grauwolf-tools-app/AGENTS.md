# grauwolf-tools-app

**Layer:** `apps` · **Status:** ADR-0118. The lean program for building and distributing tools: binary `grauwolf-tools` (`src/main.rs`) on the library `grauwolf_tools_app`. The package is not called `grauwolf-tools` because the domain crate has that name; the program is. Commands (same arguments, output and exit codes as `grauwolf tools …` had): `pull`, `inspect` (OCI and `git+…` references), `keygen`, `pack`, `push` (`--sign-key`), `build` (crates generated with `--tool-sources`, `--format text|json`), `lock` and the new `validate <package folder>` (checks `grauwolf-tools.json` as `pack` reads it and `src/<tool>.rs` of every tool – present, UTF-8, no forbidden constructs via `grauwolf_toolbuild::guest_crate`, no module used twice – reports every problem, builds nothing, exit code 1 on a problem). `ToolsCommand` is the clap enum of all of them; `run_tools(io, command, locker)` runs one, `run(args, &Io)` / `dispatch(Cli, &Io)` the whole program. `lock` takes a `Locker` (`Fn(&Io, &Path, &BuildOptions) -> Result<LockSummary, String>`): this program passes `lock_spec_tree`, which reads the tree with `grauwolf_agent_tree::AgentTree::read` – the reader the host uses, with real `code_file`/`tool_files` content, skill directory and companion checks – and locks it with `grauwolf_toolpkg::tree_lock::lock_tree`; the only check it skips is the model provider check (`ReadOptions::providers: None`), because this program knows no providers; `grauwolf tools lock` passes a locker over the host's `AgentTree` read with its providers – same lockfile, same one-line output (`LockSummary::describe`). `Io` / `Captured` / `report` and the macros `out!`, `outln!`, `err!`, `errln!` (`#[macro_export]`, hidden) live here and are re-exported by the CLI; likewise `BuildOptions`, `CacheOptions`, `DEFAULT_CACHE`, `tool_builder`.

`inspect` shows the package metadata (ADR-0124): description, created, source, revision, license, authors, built with, rustc – from the manifest annotations, else the `grauwolf-tools.json` fields – and per tool its `limits`; the line about the source layer is `sources: included|none`.


**Tool catalog (ADR-0124), module `catalog`:** `catalog list|search <text>|show <name> [--version]` (text table or detail view, `--json`) read the index with `CatalogStore`, check its signature against the policy's `oci_keys` plus `--key` (shown as `index: signed by <fp>: valid | signed: invalid (…) | unsigned | … not checked`; with `require_signatures` anything but valid is an error) and evaluate the reader's tool policy (`setup::load_policy(None, …)`: `GRAUWOLF_TOOL_POLICY` or `grauwolf.toml` in the working directory) per entry: `allowed` / `refused: <reason>`, never stored. `catalog add <ref>`, `remove <name>@<version>`, `sync [--repository <repo>]…` (rebuild from `/v2/_catalog` or the given repositories; tags `sha256-*` ignored; other artifacts are classified by `other_than_tool_package` and counted in the summary, named as `skipped <ref>: not a tool package (<media type>)` only with `--verbose`; failures are always named) write through `CatalogStore::update` (the check for our change: entry with our digest for `add`/`sync`, no entry for `remove`; on a registry that ignores conditional writes the commands print `note: <registry> ignores conditional writes; …` once; `GRAUWOLF_TOOLS_CATALOG_SETTLE_MS` sets the wait before the check, tests use 0); `--sign-key` signs the written index. The catalog is `--catalog <registry | reference>`, else `GRAUWOLF_TOOLS_CATALOG` (`RegistryConfig::tools_catalog`), else – for `add` and `push` – `<registry of the package>/grauwolf-catalog:latest` (`resolve_catalog`). `push` adds the pushed version (`catalog::add`) unless `--no-catalog`; `--catalog` names another catalog; with `--sign-key` the written index is signed too and the key's fingerprint is recorded in the entry. A failed catalog update after a successful push is an error that says the package is pushed and how to add it.

**`new <name> [--tool <tool>] [--dir <dir>]` (ADR-0124), module `new`:** writes a package folder from `templates/` (`{{name}}`, `{{tool}}`, `{{crate}}` replaced): `grauwolf-tools.json` with description, license, authors, limits and empty capabilities, `src/<tool>.rs` (a placeholder example that upper-cases `input`; the description is "What `<tool>` does, in one sentence"), `tests/<tool>.rs` with `tests/support/build.rs`/`tests/support/lib.rs`/`Cargo.toml` (the support files sit in a subfolder and the lib has `test = false`, `doctest = false`, so `cargo test` lists only the tool's test file and runs at least its two example tests) (a test crate that `include!`s the code body wrapped in a block, so `cargo test` runs it as a plain function; grauwolf ignores these files), `README.md`, `.github/workflows/grauwolf-tools.yml` (in the image `ghcr.io/agentsw0rk/grauwolf-tools`: validate, `cargo test`, pack with `SOURCE_DATE_EPOCH` of the commit; on a tag `v<version>` push with `--sign-key` from the secret `GRAUWOLF_TOOLS_SIGNING_KEY`, which also adds the catalog entry) and `.gitignore`. Refuses invalid names and a folder that is not empty. Tests `tests/new.rs` (the slow one packs the scaffold and runs its `cargo test --offline`).

## Purpose
The tool commands as a library plus a small program, so tool authors and CI pipelines build, pack, push and lock tools without the agent runtime (model providers, sandbox, MCP, A2A, SQL, OpenTelemetry, HTTP server); the CLI delegates its `tools` subcommand here (no copy of the logic).

## Allowed dependencies
- grauwolf crates: grauwolf-agent-tree (feature `packages`: the agent tree reader, ADR-0115), grauwolf-config, grauwolf-spec, grauwolf-tools (package format, `ToolSourcesManifest`), grauwolf-toolbuild, grauwolf-toolpkg (resolvers, packing, OCI/git, `setup`, `tree_lock`); dev: grauwolf-git with `test-git-server`, grauwolf-toolpkg with `test-registry`
- **Never any other app crate** (host, server, CLI, facade): `cargo xtask check-arch` rejects it, and `tests/workspace_architecture.rs` keeps the dependency count far below the CLI's. Only the CLI depends on this crate.
- External: clap, serde_json, tokio (`rt-multi-thread`: the runtime commands block on); dev: tokio

Other dependencies only after checking against [ADR-0016](../../../docs/adr/0016-layered-architecture.md) and ADR-0118.

## Invariants
- Lean by rule (ADR-0118): everything the commands need lives in domain or adapter crates; if you need something from the host, move it down instead.
- Commands print only through the `Io` they are given; errors are plain `String` messages with exit code 1 (usage errors 2).
- The registry settings come from `grauwolf_config::RegistryConfig` (`ProcessEnv` at the entry point); `VARIABLES` in `grauwolf-config` is the one list of variables.

## Tests
- The CLI's `tests/lock_equality.rs` checks that `grauwolf tools lock` and `grauwolf-tools lock` write the same lockfile and output for a tree with a diamond, a sub-agent package and a git skill.
- `tests/commands.rs` starts the real binary (`CARGO_BIN_EXE_grauwolf-tools`) for every command; registry commands run against the in-memory `TestRegistry`; tests that compile WASM with cargo are `#[ignore = "slow: …"]`.
