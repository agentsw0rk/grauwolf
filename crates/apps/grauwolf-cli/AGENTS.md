## Structure
Library (`grauwolf_cli`) plus the thin binary `grauwolf` (`src/main.rs`: `dispatch(Cli::parse(), &Io::stdio())`). ADR-0108 stage 2a.
```
src/lib.rs            pub entry: run(args, &Io) -> ExitCode (parses, usage errors to Io), dispatch(Cli, &Io)
src/cli.rs            clap definition of the top level (Cli, Command: spec / tools / token)
src/options.rs        RunOptions, Usage (+ check_effect), defaults; CacheOptions and BuildOptions are re-exported from grauwolf-tools-app
src/output.rs         re-exports Io (stdout/stderr handle; Io::captured() for tests), out!/outln!/err!/errln!, report() from grauwolf-tools-app
src/errors.rs         runtime() and the error convention (messages are Strings, exit code 1)
src/commands/token.rs
src/commands/harness.rs harness generate (ADR-0128)
src/commands/tools.rs thin delegation to grauwolf-tools-app (ToolsCommand: pull | inspect | keygen | pack | push | build | validate | lock); only `lock` is the CLI's own: it locks the host's checked AgentTree (ADR-0115) and hands the counts to the shared `LockSummary`
src/commands/spec/    mod.rs (SpecCommand + dispatch) and one module per subcommand:
                      validate, graph, schema, build, create, generate, run, resume, chat, serve, mcp
                      loader.rs (agent_loader, service_loader, observed_loader, ConfirmTools)
                      handles.rs (tools directory, memory, approver, input parsing, service_options)
```
Commands print only through the `Io` they are given (never `println!`), so they can be tested in-process. Not yet behind `Io`: stdin (`spec chat`, the console approvers, `--confirm-tools`), the environment and the file system; those stay for the later stages of ADR-0108.

Tool sources (ADR-0095, F14.5): `spec generate --tool-sources` writes the guest crates (`grauwolf_toolbuild::guest_crate`), `tools/tools.json` and `build.rs` instead of compiling (no toolchain needed; refused with `--check` and with `tool_packages`), also with `--service`/`--dockerfile`. `tools validate <package folder>` (ADR-0118) checks a package folder without building; the whole `tools` subcommand is also the program `grauwolf-tools` (same library, `grauwolf-tools-app`). `tools build <dir> [--format text|json] [--force] [--cache] [--build-wrapper]` (`grauwolf-tools-app`, `src/build.rs`) reads `tools/tools.json`, checks the SHA-256 of every guest crate (mismatch = error naming the tool), `prepare()`s once and builds each tool with `ToolBuilder::build_sources` into `tools/<name>.wasm`; a stamp `tools/<name>.wasm.src-sha256` makes it idempotent (skip unless `--force`); exit code 1 if any tool fails; JSON `{ "tools": [ { "name", "ok", "skipped", "errors": [ { "message", "line"?, "column"? } ] } ] }` (line/column relative to the tool code). Tests: `tests/tools_build.rs`.

Harnesses (ADR-0128, `commands/harness.rs`): `harness generate <file> [--out-dir build] [--cache] [--locked] [--build-wrapper]` runs `grauwolf_host::project::generate_harness`: the harness file read with `Harness::parse_named` (errors `<file>:<pointer>: …`, invalid JSON `<file>: invalid harness JSON: …`), its `spec` resolved against the file's directory, an earlier `<out-dir>/<name>/` removed (output only, no hand edits), the same as `spec generate --dockerfile` written into it plus `GENERATED.md` (the harness file it comes from, "do not edit"); warnings of the tree on stderr, `<file>: project written to <folder>` on stdout. Tests in `tests/commands.rs`.

`spec validate` also compares the types that `agent` nodes and `for_each` agent bodies declare with the specs of the local sub-agents (ADR-0101).

Agent tree (ADR-0115): `spec validate` reports on `grauwolf_host::agent_tree::read` (cycles and sub-specs outside the root's directory fail like in a run); `spec build`, `tools lock` and `spec generate` go through `commands/spec/build.rs::resolve_tree` (read + resolve: one `grauwolf.lock` next to the root covers all nodes, keys of sub-agents `<relative spec path>#<key>`; `tools lock` does not build code; "nothing to lock" only when no node has anything to lock). The CLI keeps no walker of its own.

`spec serve --spiffe --spiffe-port --spiffe-users` (ADR-0109; `SpiffeFlags` in `commands/spec/mod.rs`, flags win over `GRAUWOLF_SPIFFE*`): starts `grauwolf_server::SpiffeInbound`, wraps the router with `with_spiffe_auth` and serves the same router on a second mTLS listener; without a token and users file on a non-local address the start is allowed with SPIFFE (JWT-SVID or certificate required). `GRAUWOLF_IDENTITY_URL` (delegation, ADR-0111) without SPIFFE is a start error (`SpiffeServiceConfig::check_identity`); with it the gate exchanges people's tokens and verifies Txn-Tokens (see grauwolf-server).

## Purpose
Command line `grauwolf spec validate|schema|graph|build|run|chat|serve|mcp|create|resume|generate`, `grauwolf harness generate`, `grauwolf login|logout`, `grauwolf identity serve|grant`, `grauwolf call` and `grauwolf token`; runs `cargo check` for generated crates (repair loop).

## Invariants
- The only place where `cargo check` is started for generated crates.
- Errors are printed with a JSON pointer. Compile errors in tool code likewise: `<file>:/tools/<i>/code:<line>:<column>: error: …` (lines relative to the tool code, F13.9).

## Tests
- Integration tests start the real binary (`CARGO_BIN_EXE_grauwolf`) in the workspace root and check output and exit code (`tests/cli.rs`, `tests/tool_packages.rs`).
- `tests/commands.rs` runs commands in-process through `grauwolf_cli::run` with a captured `Io` (validate with warnings, graph, schema, tools errors, token, argument errors of every command that is cheap to reach); add new command-logic tests there, and process tests only for what needs the real process (stdin, signals, exit status of the binary).

Credential sources (ADR-0110): `spec run|chat|resume|mcp` load through `AgentLoader::load_provisioned`, which applies the `[credentials]` section of the `grauwolf.toml` next to the spec or of `GRAUWOLF_CREDENTIALS`; `spec serve` makes the environment first (`grauwolf_host::credentials::env_for`) and uses it for the token (`GRAUWOLF_SERVER_TOKEN`), the chat API and the loader (`with_credential_env`). The CLI's Cargo feature list includes `credentials`.

`grauwolf credentials check <VAR>… | --all [--config <file>]` (`commands/credentials.rs`, `grauwolf_host::credentials::check_many`): resolves the variables (each on its own, so one failure does not hide the others; exit code 1 if any fails, errors on stderr) through the credential sources and prints, per variable, `resolved <VAR> from <file|openbao|environment> (N bytes)`; never the value. Test in `tests/commands.rs`.

`grauwolf identity serve [--port] [--mtls-port]` (ADR-0111, `commands/identity.rs`): reads `Config` (section `identity`, `SERVER_PORT`) and `SpiffeServiceConfig`, needs the workload identity (`SPIFFE_ENDPOINT_SOCKET`, else an error naming it), composes the service with `grauwolf_host::identity::service` and serves it with `grauwolf_server::identity::serve_identity`. Test `identity_serve_needs_a_workload_identity` in `tests/commands.rs`.

`grauwolf login [--tenant] [--authority] [--client-id] [--scope] [--config-dir] | --status | --print-token` and `grauwolf logout [--config-dir]` (ADR-0111, `commands/login.rs`): the device code flow through `grauwolf_host::identity::DeviceLogin` (Entra v2.0 endpoints `<authority>/<tenant>/oauth2/v2.0/devicecode|token`, default authority `https://login.microsoftonline.com`; `offline_access` is added to the scope); settings from the flags, else `GRAUWOLF_LOGIN_TENANT|AUTHORITY|CLIENT_ID|SCOPE`, else the last login. The cache `<config dir>/login.json` (config dir: `--config-dir`, `GRAUWOLF_CONFIG_DIR`, `$XDG_CONFIG_HOME/grauwolf`, `~/.config/grauwolf`; directory 0700) holds the settings, the access and refresh token and `expires_at`; it is written as a new file with mode 0600 and renamed. `--identity-url` (`GRAUWOLF_LOGIN_IDENTITY_URL`, else the last login's) is kept in the cache for `identity grant`. `--print-token` prints the access token alone on stdout (refreshed first when less than 60 s are left, the cache is updated) for `curl -H "Authorization: Bearer …"`; no other output ever shows a token (`--status` and the login show name, upn and `oid` from the unverified claims). `grauwolf token` stays the user token of ADR-0068. Test `tests/login.rs` (wiremock: pending, expired code, refresh, status, logout).

`grauwolf identity grant create --agent --trigger [--purpose]… [--valid 30d] [--max-run 4h] | list [--json] | revoke <id>` (ADR-0111 stage 3, `commands/grant.rs`; all with `--identity-url` (else `GRAUWOLF_LOGIN_IDENTITY_URL`, else the login's) and `--config-dir`): authorized by `login::current` (the cached access token, refreshed like `--print-token`); `create` runs a separate device code sign-in of the login's client and scope (`Login::grant_login`, `offline_access`), sends the refresh token once through `GrantsClient::create` and drops it – the login cache is never written. Durations `30d|4h|90m|45s`; dates as `YYYY-MM-DD HH:MM UTC`. Test `tests/grants.rs` (a real identity router with `FakeEntra` and grants in memory, mocked device code endpoint).

`grauwolf call <url> [--spiffe-id] [--grant] [--input | stdin] [--json] [--token] [--timeout 600]` (`commands/call.rs`): `/run` appended to a bare address; the credential from `grauwolf_host::identity::caller_credential` (token, else the workload identity of `SPIFFE_ENDPOINT_SOCKET`: mTLS over https, JWT-SVID for `--spiffe-id` over http, else none), the call through `call_agent`; prints `output`; exit codes 0 answered, 1 failed, 3 refused (401/403). Test `tests/call.rs` (the binary with a `FakeWorkloadApi` against the server test kit).
