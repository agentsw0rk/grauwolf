# grauwolf-host

**Layer:** `apps` · **Status:** Provisioning: `provisioning` (ADR-0114) is the one module that prepares an agent run from a loaded, resolved spec: `ProvisionedAgent::new(&spec, base_dir, ProvisionOptions)` builds once per agent – executor (`executor()`), `system_one` decider (`decider()`), started MCP servers, knowledge (with its context source, ADR-0113), the built-in groups, skills, the opened long-term memory and the sub-agents; `tools()` / `tools_for(user)` give its tools, `run(user)` a `ProvisionedRun` per run and user (`user_tools()` = memory tools, key-value store, sub-agents for that user; `facts()` for automatic memory; `directory_tools().await` reloads `tools_dir`; `extras().await` = `RunExtras`). `ProvisionOptions::new(Arc<dyn Env>)` carries the environment (the only place configuration is read from, including `command.env`), user I/O, decider, MCP tools observer, features for sub-agents, LLM cache, tool builder for `tools_dir`, the `SubAgentSupplier` port (the `AgentLoader` implements it; `with_executor`/`with_embedder` replace the providers for own providers and tests). `external`, the `builtin::tools*` constructors, `LongTermMemory::open*`/`for_spec*`, `knowledge::search_tool*`, `systemone::decider_for`, `skills::tools` and `mcp::start_servers*` are internal building blocks or gone (ADR-0114). Public besides: `providers` (executor, client, embedder), `AgentLoader`/`load_spec` (`load_provisioned` returns the `ProvisionedAgent` too), `mcp::agent_server`, `packages`, `app::RunOptions { user, features, budget, conversation, attachments, approver, frame_sink, checkpoints, resume }` for `run_provisioned`/`resume_provisioned` of generated crates (`handles(prices)` makes the `RunHandles` of `grauwolf_agents::run_handles`, `resuming(store, run_id)`; ADR-0119); `ProvisionOptions::with_prices` / `ProvisionedAgent::prices()` carry the price table: the one handed in, else the file `GRAUWOLF_PRICES` names (`config::PricesConfig`, relative to `base_dir`, read by `prices::load`, which the CLI's `--prices` uses too); `limits.max_cost` without a table fails in provisioning (ADR-0119). pgvector (ADR-0106): `pgvector::connect(variable, env)` reads the URL from the variable the spec names in `url_env`; `knowledge.store: postgres` and `long_term_memory.vector_store` go through provisioning like the file stores; without the feature a postgres store is `this build has no PostgreSQL store (feature `pgvector`)`. A spec that uses a group whose Cargo feature is off (`git`, `fetch`, `command`, `atlassian`, `mcp`, `builtin`) fails in provisioning with `this build has no … (feature `…`)`, before any credential check.


Providers (ADR-0043, ADR-0082, ADR-0083, ADR-0105): `providers::client_from_env(provider)` / `client_from(provider, env)` / `client_with(provider, &ProvidersConfig)` build the `LlmClient` for `model.provider` from environment variables: `OLLAMA_HOST` (default `http://localhost:11434`) and `OLLAMA_THINK` (`true`/`1` or `false`/`0`, anything else ignored), `OPENAI_API_KEY` + optional `OPENAI_BASE_URL`, `ANTHROPIC_API_KEY`, `GEMINI_API_KEY` + optional `GEMINI_BASE_URL`; the OpenAI-compatible presets (`providers::OPENAI_COMPATIBLE`: `openrouter`, `deepseek`, `mistral`, `groq`, `dashscope`, `xai`; their variables are `config::COMPATIBLE_VARIABLES`) use `<NAME>_API_KEY` and optional `<NAME>_BASE_URL` via the OpenAI adapter; `providers::BUILTIN` lists the names the build knows. Provider `bedrock` (feature `bedrock`): `ProvidersConfig` reads `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN`, `AWS_REGION` (else `AWS_DEFAULT_REGION`, else `us-west-2` in the client), `AWS_BEARER_TOKEN_BEDROCK` (wins over the access keys) and `BEDROCK_BASE_URL` (empty values count as unset); missing credentials name the variables. `ProviderError::{Unknown, MissingVariable, NoEmbeddings}` (an embedding model with `bedrock` is `NoEmbeddings`). `providers::executor_from_env(provider)` / `executor_from` / `executor_with` build the `PromptExecutor` with retries (`RetryPolicy::default()`, `runtime::TokioClock`); `providers::executor_for(providers, env)` / `executor_for_config` builds one with clients for several providers; `executor_builder_for(providers, env)` / `executor_builder_with` return the builder (for `.cache(..)`). `providers::embedder_from(provider, model, env)` / `embedder_with` return a `grauwolf_rag::Embedder` (`ollama` via `/api/embed`; `openai` via `/embeddings` with `OPENAI_API_KEY`/`OPENAI_BASE_URL`; the compatible presets likewise with their variables; `gemini` via `:batchEmbedContents` with `GEMINI_API_KEY`/`GEMINI_BASE_URL`). Re-exports of the facade: `agents`, `graph`, `interpreter`, `llm`, `prompt`, `rag`, `spec`, `tools`, `toolbuild`, the macros `tool`/`toolset` (feature `macros`, on by default; `grauwolf_macros::facade_*`, generated code uses `::grauwolf::tools`, ADR-0003 addendum) and the adapters `ollama`/`openai`/`anthropic`/`gemini`/`bedrock` and `sandbox` via Cargo features (all on by default).

With feature `sql` (SQLite/Postgres, ADR-0048): `memory::sql_chat_history_store(url)` and `checkpoints::sql_checkpoint_store(url)`. `attachments::from_file(path)` reads a file as an `Attachment` (media type from the extension: png, jpg/jpeg, gif, webp, pdf, wav, mp3; at most `MAX_ATTACHMENT_BYTES` = 20 MB; base64; ADR-0081). `otel::OtelTracing::init(endpoint)` (feature `otel`): OTLP/HTTP export with a batch processor; without an endpoint from `OTEL_EXPORTER_OTLP_*`; service name from `OTEL_SERVICE_NAME` (default `grauwolf`); `feature(agent_name, content)` returns the feature of the tracing (`OtelFeature`, ADR-0049); `shutdown()` sends open spans (blocking); `init_with(endpoint, &TelemetryConfig)` takes the section. `features::JsonlEventLog::new(out)` writes events as JSON lines to a `Write` (errors are discarded). `runtime::TokioClock` implements the port `Clock`.

Specs, code and tool builds: `read_spec(file)` reads and parses without checking (for `spec validate`, so that all errors appear together); `load_spec(file)` = `read_spec` + check (errors with pointer as `<file>:<pointer>: …`, otherwise `<file>: …`; ADR-0080; resolves `tools[].code_file` relative to the spec, exactly one of `code`/`code_file`; appends `tool_files`, whose `code_file` is relative to the tool file; ADR-0073); `warning_lines(file, spec)` gives the warnings. `spec_schema()` is the schema of the spec including `tool_files`/`code_file` (`code` is then not required, and `transform` of edges knows `code_file`). Code in graphs (ADR-0102, F14.14): the loader resolves `code_file` in the params of `code` nodes and `on_code` conditions and in the `transform` of edges (main graph and subgraphs, errors with the pointer). `build_tools(file, spec, builder)` builds the tools and then the `AgentSpecExt::code_pieces()` (artifact names = piece names; errors with file and JSON pointer; compile errors as `<file>:<pointer of the code>:<line>:<column>: …`); the loader builds them at run start like tools (cache). Test `tests/code_files.rs`. `builder::ToolBuildChecker::new(cache)` implements the port `SpecChecker` of the builder agent with `grauwolf-toolbuild` (compile errors become a `SpecIssue` at `/tools/<i>/code` with line/column; the build runs in `spawn_blocking`; `from_builder` for configured builders, e.g. with a wrapper). `tools_dir::ToolsDir::new(dir, builder, taken)` (feature `sandbox`, ADR-0074): `load()` reads all `*.json` in the folder (format per ADR-0073; `code_file` relative to the tool file), builds them with the `ToolBuilder` (cache via the checksum) in `spawn_blocking`, instantiates them in the sandbox and returns `LoadedTools { tools, skipped }`; a missing folder counts as empty; not JSON, no tool definition, a name that is not snake_case, compile errors and names taken from `taken` or duplicated end up in `skipped` with the file name (provisioning reports them through `with_skipped_tool_report`). `self_tools::BuildingToolFactory::new(builder)` (feature `sandbox`, ADR-0075) implements the port `ToolFactory`: builds with `prepare()` + `build()` in `spawn_blocking` (cache), instance in the sandbox; every error as text (compile errors with `line …, column …`); `with_save_dir(dir)` saves built tools as `<name>.json` + `<name>.rs` (format ADR-0073) in the tools folder. The `AgentLoader` gives specs with `self_tools` this factory (with `save` to `tools_dir`). `env::expand(value)` / `expand_with(value, &dyn Env)` replace `${VAR}` in the headers of MCP servers and A2A agents (a missing variable is an error).

Built-in tools (ADR-0046, ADR-0098, ADR-0104; provisioning builds them, `builtin` holds the pieces): feature `builtin` (file and user tools, `think`, `fetch` from `builtin_tools.fetch`, todo tools, key-value tools, skills and the Jira, Confluence and git tools; includes `grauwolf-atlassian`), the groups `git`, `fetch`, `command` and `atlassian` have their own features, all in `default`. File tools work below `builtin_tools.root` relative to `base_dir`; user tools go through `UserIo` (re-exports `ConsoleUserIo`, `FileTools`, `UserTools`). The key-value store is the file `<root>/kv.json`, with a user `<root>/users/<hex>/kv.json` (`conversation_key(user, "kv")`). Atlassian: `AtlassianClient` with `ATLASSIAN_EMAIL`, `ATLASSIAN_API_TOKEN`; git: `GitTools`/`GitConfig` with `GIT_TOKEN` (only with `use_token`), `GIT_AUTHOR_NAME`/`GIT_AUTHOR_EMAIL`, working in the directory below `builtin_tools.root` (a symlink leading out is refused); `command`: the `run_command` tool (ADR-0099, `command.env` values from the environment). Missing credentials or a missing `git` program fail in provisioning, i.e. before the run, with messages naming the variable. A spec that uses a group whose feature is off fails with `this build has no git tools (feature `git`)` (likewise `command tool`, `fetch tool`, `Jira tools`/`Confluence tools` with `atlassian`). `GitConfig`/`GitTools`/`AtlassianClient` are re-exported only with their feature.

System One: with feature `systemone` (default), provisioning picks the `system_one` decider of a spec's decision nodes: the one handed in (`ProvisionOptions::with_decider`, `AgentLoader::with_decider`), otherwise the `systemone::SystemOneClient` from `RKEV_BASE_URL` (+ optional `RKEV_API_KEY`) wrapped in `RetryingDecider` with `RetryPolicy::default()` and `TokioClock`; none for specs without such nodes; a spec that needs the service but finds no `RKEV_BASE_URL` fails with `systemone::DeciderError::MissingBaseUrl` and a clear message, so the run fails before it starts (ADR-0100).

Knowledge, memory and MCP/A2A (internal building blocks of provisioning, ADR-0114; the modules `knowledge` and `long_term_memory` are crate-private): knowledge reads the spec's sources – files, directories recursively (sorted; UTF-8, otherwise an error with the path) and `urls` (ADR-0113: `urls::load_url(url, known validators, indexed)` fetches with a conditional request through `grauwolf_tools_web::fetch_page` (feature `fetch`; without it `this build has no HTTP client for knowledge URLs`), the chunks of a URL are named by the URL, the index file keeps the validators per URL, `304` keeps the indexed content, a failing URL keeps indexed content with a warning on stderr and otherwise fails with `knowledge URL <url>: <reason>`) – splits them with `chunk_size`, indexes them in memory and offers the search tool (source = path relative to `base_dir`; `min_similarity` is applied by the retriever; `knowledge.inject` puts hits into the context before each request, `knowledge.tool_enabled` turns the tool off). With `knowledge.index` a JSON index keeps model, chunk size and per file an FNV-1a checksum + chunks + embeddings: only new or changed files are embedded, removed ones dropped, written atomically (ADR-0057). With `knowledge.store: postgres` the chunks go into pgvector (collection `<spec name>/<knowledge tool>`, incremental, validators in the store). Long-term memory: the same file (normalized path) shares one store within the process; `tools(user)` returns `[remember, recall]` for exactly one scope (a user, or with `None` the shared scope; ADR-0059) and `facts(user)` the same scope as a `FactMemory` for automatic recall/remember (ADR-0069); no memory tools with `long_term_memory.tools: false`. The file `store` (relative to `base_dir`; `{ model, facts: [{ user?, chunk, embedding }] }`, loaded when opened – an embedding model other than `<provider>:<id>` in the file is an error; written atomically after each entry; the same text is stored only once per scope; ADR-0058); `long_term_memory.vector_store` (pgvector) opens with one probe embedding for the dimension, honors `ttl_days` and `min_similarity` and keeps a per-user area like the file store. `mcp`: the servers of a spec connect via stdio, Streamable HTTP or, with `transport: "sse"`, the older HTTP+SSE transport (ADR-0112; test `tests/mcp_sse.rs`); `${VAR}` in `headers` comes from the environment (a missing variable is an error); with `resources: true` the resource tools are offered (ADR-0051); declared tools that are missing are an error with the existing names. `mcp::{McpClient, McpServer, McpResource, McpPrompt, McpPromptArgument}` are re-exported. `mcp::list_tools(name, &McpServerSpec, env)` connects to one server like a run does and lists every tool it offers (grauwolf studio's discovery, ADR-0126 decision 13; test in `tests/mcp_sse.rs`). `mcp::agent_server(spec, base_dir, tools)` builds an agent's MCP server with the resources `grauwolf://<name>/spec` and, for the documents of `knowledge.sources`, `grauwolf://<name>/knowledge/<path>` (UTF-8 only) and the prompt `<name>` (system prompt + `{request}`; ADR-0089). Sub-agents with `url` come via `grauwolf_a2a::A2aClient` (feature `a2a`; headers with `${VAR}` via `env::expand_with`; ADR-0055).

Agent tree (ADR-0115, features of the loader): The agent tree lives in `grauwolf-agent-tree` (shared with `grauwolf-tools-app`, ADR-0118); `agent_tree` re-exports it and adds `agent_tree::read(file)` (or `read_spec(spec, base_dir)` for a root in memory), which is `AgentTree::read` with the host's `read_options()` (the built-in providers of `providers::BUILTIN` and the skill directory check; the crate's own `AgentTree::read` takes `ReadOptions`) – the read phase over a spec and its local sub-agents: every spec read and checked once (`ReadErrors` collects all errors as `<file>:<pointer>: …`, warnings in `tree.warnings()`), a sub-spec under several parents is one node (`Child::Local { node }` is the same index), cycles are errors naming the chain, sub-specs outside the root's directory (`..` out of it or absolute) are errors, `Child::Remote` (A2A) is a leaf, per node `companions()` (below the spec directory) and sub-agent signatures are checked. `AgentNode` gives `file`, `relative` (place in an image's `app/`), `spec`, `children`, `base_dir`.

Resolve phase (in `grauwolf-agent-tree`): `AgentTree::resolve(&ResolveOptions { builder, locked, config })` (network, lockfile) localises git skills, resolves tool packages and builds code tools once per node (`node.resolution()`: localised `spec`, `package_tools`, `artifacts`, `skills`). One `grauwolf.lock` next to the root (`tree.lock_path()`) covers the tree: keys of the root are unchanged, keys of every other node are `<spec path relative to the root's directory>#<key>` (e.g. `agents/writer.json#git+…@v1`); the tool policy of the root applies to all nodes; a lockfile next to a sub-spec gives a warning and is not used; the lockfile is not touched when no node has packages or git skills; `locked` fails with `… is out of date` instead of writing.

Copy into an image (ADR-0115, ADR-0096; in `grauwolf-agent-tree`): `AgentTree::copy_into(app, builder)` copies a resolved tree into the `app/` of a generated image: per node the companion files and the resolved git skills (`skills-git/<index>` next to the spec), per node but the root the spec document (tool files and code files inlined, git skills replaced; `AgentNode::image_spec`), and in `APP_TOOL_CACHE` (`.grauwolf/tools`) the built code of the sub-agents (`artifacts/<hash>.wasm`, `toolchain` = `ToolBuilder::export_toolchain`, the shared `Cargo.lock`) and the package entries their lock entries name, plus `grauwolf.lock` when a sub-agent has tool packages. The generated service loads sub-agents with `AgentLoader::for_provisioning` (`locked`) from that cache without network, toolchain or git; `ResolveOptions::resolve_root: false` (what `AgentLoader::supply` uses, the root is embedded) keeps the root's lock entries and builds nothing for it. The tool policy is applied when the image is built, not in the image.

Loader: `loader::AgentLoader::new(tool_builder)` (features `sandbox`+`mcp`+`builtin`+`a2a`) loads specs as agents: builds tool code, reads and resolves the agent tree (`AgentTree`, ADR-0115), provisions each node through `ProvisionedAgent` and serves `SubAgentSupplier` from the tree's nodes: a sub-agent that several parents name is loaded and provisioned once and shared (one set of MCP servers, one knowledge index); `AgentLoader::for_provisioning` (generated code) loads with `locked`, `AgentLoader::supply(spec, base_dir)` reads a tree from a root in memory; `with_feature`, `with_agent_features(fn(&spec))`, `with_interceptor`, `with_tool_approval(tools)` (requires approval in every agent; sub-agents reject; ADR-0061), `with_prices(prices)` (costs in every agent, ADR-0071), `with_budget(budget)` (a budget per agent, sub-agents included; ADR-0072), `with_user_io`, `with_decider`, `with_llm_cache`, `with_skipped_tool_report`, `with_env`, `with_chat_api_mode`, `with_locked`. `AgentLoader::provision_options()` returns the options it provisions with.

Tool packages (ADR-0107): feature `packages` (default; implies `sandbox`) re-exports `grauwolf_toolpkg` as `toolpkg`; `packages::git_resolver` / `load_allowed_signers` (for `tools pull|inspect` of git references), `packages::resolve_tools(file, spec, tool_cache, locked)` resolves the `tool_packages` of a spec against `grauwolf.lock` next to it (`packages::lock_path`); `resolve_tools_with(…, config, builder)` takes the `ToolBuilder` that compiles git packages from their sources (ADR-0107 stage 3; a private `ModuleBuilder` adapter over it, also used by `pack_folder` through `grauwolf_toolpkg::pack_sources`) and `RegistryConfig::git_token` (`GIT_TOKEN`); `AgentTree::resolve` does it once per node, passes the tools via `Interpreter::with_package_tools` and has `with_locked(bool)`; without the feature a spec with `tool_packages` is an error. `packages::pack_folder(dir, builder)` builds the tools of a package folder (`grauwolf-tools.json` + `src/<tool>.rs`) and returns a `PackedPackage` (stage 2, `grauwolf tools pack`); `packages::load_packed(path, builder)` reads an image layout directory (has `oci-layout`) or packs a package folder, `packages::push_package(reference, &packed)` pushes it with the credentials of the environment and returns `<reference>@sha256:…` (`grauwolf tools push`).

Configuration (ADR-0108, stage 4b): `config::{Env, ProcessEnv, MapEnv}` (the port, `RegistryConfig` and `VARIABLES` live in `grauwolf-config` since ADR-0118 and are re-exported here under the same paths; every `Fn(&str) -> Option<String> + Send + Sync` is an `Env`), `config::Config::from_env(&dyn Env)` with the sections `providers` (`ProvidersConfig`: Ollama, OpenAI, Anthropic, Gemini and the OpenAI-compatible variables `COMPATIBLE_VARIABLES`, `chat_api_mode`), `registry` (`GRAUWOLF_REGISTRY_AUTH`, `DOCKER_CONFIG`, `HOME`, `PATH`, `GIT_TOKEN` for git packages, `GRAUWOLF_TOOL_POLICY` = `tool_policy`: policy file), `atlassian`, `git` (`GitEnvConfig`), `system_one`, `service` (`ServiceConfig`, ports parsed, `GRAUWOLF_EVENTS` as `events` (same values), `GRAUWOLF_OTEL` / `GRAUWOLF_OTEL_CONTENT` as `otel` / `otel_content`: `1`/`true`/`0`/`false`, any other value is an error naming the variable (ADR-0123); `from_lookup` is the only fallible one), `chat_api` and `telemetry`; each section has `from_env` and `from_lookup`. `config::VARIABLES` is the one table of variables (a test keeps it equal to what `Config` reads and to `docs/user-guide/reference-cli.md`). Core functions take sections: `providers::{client_with, executor_with, executor_for_config, executor_builder_with, embedder_with}`, `systemone::decider_with` (internal), `packages::{registry_auth, load_policy (`GRAUWOLF_TOOL_POLICY`, else `grauwolf.toml` next to the spec or, without a spec, in the working directory; none = no policy), resolver_for (resolver with that policy; `resolve_tools_with` and `tools pull|inspect` use it), resolver_with, resolve_tools_with, push_package_with}`, `otel::OtelTracing::init_with`, `env::expand_with`; the older closure variants of the `providers` functions remain (`client_from`, `executor_from_env`, …). `AgentLoader::with_env(Arc<dyn Env>)` (default `ProcessEnv`; the CLI passes it explicitly) and `with_chat_api_mode(bool)` set what the loader reads. Chat API mode (`OLLAMA_BASE_URL` stands in for a missing `OLLAMA_HOST`, `providers::ollama_host(&ProvidersConfig)`) is `ProvidersConfig::chat_api_mode`: on with `GRAUWOLF_CHAT_API=1|true` in the environment or `with_chat_api_mode(true)`. The observer of MCP tool lists (`mcp_observer::McpToolsObserver`) is passed explicitly: `AgentLoader::with_mcp_tools_observer`, `ProvisionOptions::with_mcp_tools_observer` take an `Option`; the host keeps no process-wide state and knows no chat API or observations. `ProvisionOptions::with_agent_features(Option<AgentFeatures>)` (type in `app`, re-exported by `loader`) gives the loader a generated crate builds (`AgentLoader::for_provisioning`) a feature factory by spec for the sub-agents it loads (the main agent takes `RunOptions.features`; ADR-0094). Variables read elsewhere: `OTEL_EXPORTER_OTLP_*` (OpenTelemetry SDK), `CARGO`/`RUSTC` (tool build, CLI `generate --check`).

Skills (ADR-0103, feature `builtin`): `skills::{roots, library}(spec, base_dir)` and the internal `skills::tools` load the local `skills` directories (relative to the spec) into a `grauwolf_builtin_tools::SkillLibrary`; provisioning appends `load_skill`/`read_skill_file`. A git source is an error there (`/skills/<i>: git skills are not resolved to a local directory`): the loader and the generator turn git sources into local directories first. Git sources are resolved by the agent tree's resolve phase (`AgentTree::resolve`: against `grauwolf.lock`, cache `<tool cache>/packages/skills-<commit>…` through `packages::skills_resolver` = resolver with policy, `GIT_TOKEN` and no module builder; the node's `resolution().spec` has them as absolute local directories of the cache; `skills::replace_with_dir`; without the feature `packages` a git skills source is an error); `skills::check_local(spec, base_dir)` checks the local directories for `spec validate`. Test `tests/git_skills.rs` (loader); the resolving is tested in `grauwolf-agent-tree/tests/git_skills.rs`.

Flows (ADR-0101): the read phase of the agent tree collects the (input, output) types of the local sub-agents and fails with `AgentSpec::check_sub_agent_types` errors if an `agent` node or `for_each` agent body declares other types.

Workload identity outbound (ADR-0109): `spiffe::client_auth(env, "sub-agent 'x'", &AuthSpec)` turns `auth.spiffe` of `agent_tools`/`mcp_servers` into a `ClientAuth` (mtls: `id`/`ids`/`trust_domain` as `SpiffeMatch`; jwt: audience); `spiffe::workload(env)` starts the live identity at `SPIFFE_ENDPOINT_SOCKET` once per socket and process (a deliberate exception to "no process-wide state": the Workload API streams run once). Without the variable the error names the target and the variable. Used by `mcp::connect` and the remote branch of `AgentLoader` (sub-agents, `agent` nodes and `for_each` alike; generated code provisions through the same host code). `grauwolf-spiffe` is a plain dependency (the feature `credentials` no longer enables it).

`RunOptions.trace_parent` (ADR-0123, next to `caller`): the caller's trace context; `handles()` passes it to `RunHandles`, so a generated service continues the caller's trace once tracing is on (a `GeneratedAgent` maps `RunExtras.trace_parent` to it).

## Purpose
Composition root (ADR-0108, stage 4a): assembles a runnable agent from a spec – loader, providers from the environment, tool provisioning (built-in, MCP, knowledge, memory, tools directory, self-built tools, tool packages), file and SQL stores, prompt cache, OpenTelemetry and the System One decider. The facade `grauwolf` re-exports every module under the same path (`grauwolf::loader`, `grauwolf::providers`, …); the Cargo features of the facade forward to those of this crate (same names). Also the tokio adapter for the port `Clock` (`runtime::TokioClock`); there is no `Spawn` port.

`project` (ADR-0096, ADR-0128): `generate_harness(file, out_dir, builder, locked)` (async) writes a harness project into `<out_dir>/<name>/` – the harness file read with `Harness::parse_named`, an earlier folder removed only after that, the tree read and resolved, the service crate with the `Dockerfile` of this version (`BUILDER_CRATES`), `app/` and `NOTE_FILE` (`GENERATED.md`); returns the harness, the folder and the tree's warnings; used by `grauwolf harness generate` and grauwolf studio. `write_crate(generated, out)` writes a `GeneratedCrate`. `copy_app_files(tree, builder, app)` – what a generated service reads at run time in `app/` (the chat API's `SIGNATURE_FILE`/`NAMES_FILE` next to the root spec, `EGRESS_FILE` from `grauwolf-egress`, the resolved tree through `AgentTree::copy_into`); used by `spec generate --dockerfile` of the CLI. `grauwolf_server::chat_api` re-exports the two file names. `generate_harness`, `HarnessProject` and `copy_app_files` need the features of `agent_tree` (`mcp`, `builtin`, `sandbox`, `a2a`); the file names, `BUILDER_CRATES`, `NOTE_FILE` and `write_crate` are in every build (generated crates build the host with fewer features – `spec generate --check` in the slow CLI tests catches a module that is not gated).

- Never: grauwolf-server, grauwolf-cli, grauwolf (the facade) – the dependency direction is host ← facade/server/CLI (ADR-0108, stage 4d; checked by `cargo xtask check-arch`)

Other dependencies only after checking against [ADR-0016](../../../docs/adr/0016-layered-architecture.md).

## Invariants
- Composition only; no HTTP routes, no CLI. The process environment is read only through `config::ProcessEnv`, in the convenience wrappers and at the entry points that call them; everything else takes a `config` section or an `Env`, so tests use `MapEnv` and never change the process environment.
- Public paths are re-exported by the facade under the same names: do not rename a module without changing the facade.

Built-in dispatch (ADR-0117): `builtin::build` loops over `BuiltinToolsSpec::groups()` (table order of `BUILTIN_GROUPS`) with an exhaustive `match` on `BuiltinGroup`; the `cfg`-gated builders keep the `this build has no …` errors. `tools_dir::taken_names(spec)` (names a `tools_dir` tool must not override) is the whole tool namespace (`AgentSpec::tool_namespace()`), including package and self-build tools.

Conversation stores of a generated service (ADR-0119): `ServiceConfig` has `conversations_dir` (`GRAUWOLF_CONVERSATIONS_DIR`, relative to `data_dir`) and `conversations_db` (`GRAUWOLF_CONVERSATIONS_DB`, a secret URL); both set is an error from `from_lookup` naming both variables (test `conversations_live_in_a_directory_or_a_database_but_not_both`).

Credential sources (ADR-0110, stage 2; Cargo feature `credentials`, in `default`): `credentials::env_for(base, spec file)` returns `base` unchanged without a `[credentials]` section, else a `grauwolf_credentials::CredentialEnv` (variables from `file:` / `openbao:` sources, rest from `base`); without the feature a credentials configuration is an error. `AgentLoader::load_provisioned` (hence `load`) builds that environment once per loader (`credential_env(file)`, shared by clones; `with_credential_env(env)` hands in one made elsewhere) and loads the agent, its sub-agents and the provisioning with it, so every `Config` section reads through the sources. Tests: `tests/credentials.rs`, `credentials::tests`.

ADR-0110 stage 1 (provisioning): `builtin::resolve_auth` (async, before the sync tool build) turns `builtin_tools.fetch.auth` / `git.auth` into `ClientAuth`s (`spiffe::client_auth`; errors name `builtin_tools.fetch.auth.<host>` and the missing `SPIFFE_ENDPOINT_SOCKET`); `Settings.fetch_auth/git_auth` hand them to `fetch_tool`/`git_tools` (generated crates provision through the same code). `spiffe::workload_env(env, what)` gives `SPIFFE_ENDPOINT_SOCKET` (+ `SPIFFE_FETCH_TIMEOUT`) for `mcp_servers.<n>.workload_api` (stdio child via `McpClient::spawn_with_env`) and `builtin_tools.command.workload_api` (added to the program's environment); without a socket the provisioning error names the server or `builtin_tools.command.workload_api`. Tests: `tests/workload_identity.rs`.

`RunOptions.on_behalf_of` (ADR-0111) goes into `RunHandles.on_behalf_of`, like `caller` and `trace_parent`.

Delegation (ADR-0111): `identity::agent_client(&SpiffeServiceConfig, identity)` builds the agent's `IdentityClient` from `GRAUWOLF_IDENTITY_URL` (`None` without it): `https://` with mTLS (server `GRAUWOLF_IDENTITY_SPIFFE_ID`, else any ID of the own trust domain), `http://` with a JWT-SVID for the audience `GRAUWOLF_IDENTITY_SPIFFE_ID` (required); `identity::service(&IdentityServiceConfig, identity)` (feature `credentials`) composes `grauwolf identity serve`: `EntraVerifier`, `TransitSigner` with an `OpenBaoClient` login by the service's JWT-SVID, the watched policy file; with `GRAUWOLF_IDENTITY_GRANT_CLIENT_ID` also grants (`OpenBaoGrantStore` in `GRAUWOLF_IDENTITY_GRANT_KV_MOUNT`, default `kv`, with the same OpenBao login; `PublicClientRefresh` at `GRAUWOLF_IDENTITY_GRANT_TOKEN_URL` or the issuer's discovery, scope `IdentityServiceConfig::grant_scope()`); a missing required variable is an error naming it. `config::IdentityServiceConfig` (`Config.identity`; `GRAUWOLF_IDENTITY_AUDIENCE` is a comma-separated list: `audiences`, `required_audiences()`; `GRAUWOLF_IDENTITY_*`, defaults scope `access_as_user`, Transit mount `transit`, OpenBao audience `openbao`, mount `jwt`; `required(value, variable)`) and `SpiffeServiceConfig.identity_url` / `identity_spiffe_id`; `SpiffeServiceConfig::check_identity()` refuses `GRAUWOLF_IDENTITY_URL` without `GRAUWOLF_SPIFFE` ("GRAUWOLF_IDENTITY_URL needs GRAUWOLF_SPIFFE"). `identity::caller_credential(env, url, expected spiffe id?, token?)` builds the credential of `grauwolf call` (token, else the workload identity: mTLS over `https://` – server `expected`, else the own trust domain –, a JWT-SVID for `expected` over `http://`, else none). `identity` also re-exports `GrantsClient`, `GrantRequest`, `Grant`, `call_agent`, `CallerCredential`, `CallAnswer` and the device code login (`DeviceLogin`, `DeviceEndpoints`, `DeviceCode`, `OAuthTokens`) and `peek_claims` for `grauwolf login`. Dependencies: grauwolf-identity (always), grauwolf-openbao (feature `credentials`). Test `tests/identity.rs`.
