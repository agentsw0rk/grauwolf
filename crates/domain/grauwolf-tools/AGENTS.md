# grauwolf-tools

**Layer:** `domain` · **Status:** `knowledge_context_of(tools, name)` finds the `KnowledgeContext` of the search tool called `name` (`DynTool::knowledge_context`); the interpreter and generated code both use it for `knowledge.inject` (ADR-0116). `ToolSourceKind` (`tool`, `code`, `condition`, `transform`; ADR-0102) in `ToolSourceCrate` and the optional `kind` of a `tools/tools.json` entry (omitted for tools, so old manifests stay valid). Tools with a state (ADR-0098): `DynTool::state_key()` (default `None`) and `call_with_state(args, &mut Value)`; `ToolRegistry::find(name)`. `Tool` (typed), `DynTool` (JSON → text, blanket impl), `ToolRegistry` with `descriptors()` (JSON schema via schemars) and `extended(tools)` (same-named tools are replaced, ADR-0059), `ToolError`; `ToolShelf` (the shared, growing tool layer of a run; `put` assigns each name only once) is attached to the registry via `ToolRegistry::with_shelf` – `descriptors()`, `call()`, and `contains()` see its tools, `is_on_shelf(name)` recognizes them, clones share them (ADR-0075); `put_made(tool, definition)` remembers the `NewTool` definition (serde) of built tools, and `definitions()` or `ToolRegistry::self_made()` return them for checkpoints (ADR-0077). Port `ToolFactory` (`create(NewTool { name, description, args, code })` → `DynTool` or an error text for the model; ADR-0075). Port `ToolRuntime` with `ToolArtifact`; `ToolRegistryBuilder::shared` for tools shared from runtimes. **Goal:** `ToolContext` `__private` re-exports serde, schemars, and `BoxFuture` for code generated by `#[tool]` (no stable API).

Tool packages (ADR-0107): `PackageManifest` (`grauwolf-tools.json`: format, name, version, `abi`, tools with definition and module file name; `from_json` validates, `from_source_json` reads the file of a package folder with `format`, `abi` and the module file names optional – derived as `<tool>.wasm` –, `PackageError`; optional metadata `description`, `license`, `authors`, `source` and per tool `limits` (`ToolLimits { memory_mib, fuel, time_ms }`, 0 refused, `stricter(other)`) and `capabilities` (must be empty under ABI v1: `UnsupportedCapabilities`) – all written only when set, so a manifest without them serializes as before; ADR-0124), `PACKAGE_FORMAT`, `TOOL_ABI`, `MANIFEST_FILE`. Policy (stage 4): `ToolPolicy::parse(text)` reads the `[tool_packages]` table of `grauwolf.toml` (pure; unknown keys and `require_signatures` without a key are `PolicyError`), `check_oci(registry, repository)` and `check_git(url)` apply the allowlists (prefix matches only at segment boundaries, host part case-insensitive, `.git` and the scheme ignored; missing list = any, empty = none) and return a `PolicyViolation` text. Key files and signature checks belong to the adapters.

Tool sources (ADR-0095): `ToolSourceCrate` (the guest crate of a tool as text: name, `Cargo.toml`, `src/lib.rs`; `hash`: SHA-256 of both files, computed by the producer, `grauwolf-toolbuild`; the domain has no hash function) and `ToolSourcesManifest` (`tools/tools.json`: `format`, per tool `name`, `module`, `sha256`; `for_crates`, `from_json`, `to_json`, `ToolSourcesError`), `TOOL_SOURCES_FILE`, `TOOL_SOURCES_FORMAT`.

System prompt additions (ADR-0103): `DynTool::prompt_addition()` (default `None`; the skill list of `load_skill`) and `ToolRegistry::prompt_addition()` (the additions joined by a blank line); `LOAD_SKILL_TOOL` is the name the agent watches for `skill_loaded`.

Sub-agents as flow steps (ADR-0101): `DynTool::call_step(input, parent: Option<StepHandles>)` runs a tool as a deterministic step (default: text becomes `{ "request": text }`, the result is the tool's text as a JSON string); `StepHandles` is an opaque `Arc<dyn Any>` for the calling run, which agent tools in the interpreter override to adopt it.

Package limits (ADR-0124): `ResolvedTool.limits` (`ToolLimits` of the package's tool) and `ToolRuntime::instantiate_limited(artifact, descriptor, &limits)` – the default ignores the limits; a runtime with its own limits applies the stricter of both.


Tool catalog (ADR-0124), module `catalog`: `CatalogIndex { format, updated, entries }` (entries keyed by `<name>@<version>`; `from_json` checks `CATALOG_FORMAT`, `to_json`, `upsert` → changed?, `remove`, `list` (name, then version), `search(text)` (name, description, tool names and descriptions, ignoring case), `find(name, version?)` (newest without a version), `versions`), `CatalogEntry` (reference with digest, metadata, `CatalogTool`s with module digest, size, limits, capabilities, `CatalogSignature { signed, fingerprints, signatures: [{ payload, signature }] }`), `compare_versions`, `CATALOG_ARTIFACT_TYPE`, `CATALOG_REPOSITORY` (`grauwolf-catalog`), `CATALOG_TAG`. Pure: no IO, no crypto; whether a reader's policy allows an entry is decided in the adapter, never stored.

## Invariants
- Tool errors are returned to the LLM as a tool result, not as a panic.
- `ToolRuntime` takes artifacts and capabilities, never source code (ADR-0014, ADR-0024).
- Concurrent tool calls run via `join_all`, not `JoinSet` (ADR-0026).
- `with_trace_headers(headers, future)` / `current_trace_headers()` (ADR-0123): the `(name, value)` pairs of the W3C Trace Context for the HTTP clients of a call (A2A, MCP). The scope belongs to the future (a `poll_fn` that sets a thread-local while it polls), so it works on every runtime, holds across `.await`, and is not seen by spawned tasks; empty headers keep the enclosing scope. No OpenTelemetry types here.

Delegation (ADR-0111): trait `Delegation { txn_token() }` (the run's Txn-Token, renewed by the holder before it expires), `with_delegation(Some(holder), future)` / `current_delegation()` / `delegation_header()` (`(TXN_TOKEN_HEADER, token)` = `Txn-Token`) – the same future-bound scope as the trace headers, but its own slot, so a tool call's trace scope does not hide it. The service wraps the whole run; the HTTP clients of internal calls (A2A, MCP over HTTP with a workload identity, `fetch` to hosts with `auth.spiffe`) add the header. The token never goes through tool arguments.
